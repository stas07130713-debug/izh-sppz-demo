# ИЖ СППЗ — единое техническое задание на доработку для Codex

## Общая задача

Необходимо доработать существующее приложение **«Интерактивный журнал систем противопожарной защиты (ИЖ СППЗ)»**.

Это не новая разработка с нуля. Сначала проанализировать текущий код, существующую структуру данных, компоненты интерфейса и уже реализованные функции. Максимально переиспользовать имеющуюся архитектуру и не создавать дублирующие сущности, формы, справочники и таблицы, если аналогичный механизм уже существует.

Ключевой принцип системы:

**дерево объектов ↔ план ↔ журнал ↔ карточка элемента ↔ техническое состояние ↔ чек-листы ↔ заявки ↔ история действий**

Все представления должны работать с одними и теми же сущностями и данными. Нельзя хранить отдельные несинхронизированные копии одного элемента для плана, журнала и карточки.

Перед началом доработок определить:

1. что уже реализовано полностью;
2. что реализовано частично;
3. что отсутствует;
4. какие компоненты и структуры данных можно переиспользовать;
5. требуются ли миграции БД;
6. как выполнить миграции без потери существующих пользовательских данных.

---

# 1. Размещение элементов без загруженной подложки

Пользователь должен иметь возможность создавать, редактировать и использовать элементы СППЗ даже тогда, когда план-подложка ещё не загружен.

Пока подложки нет:

- элементы не должны располагаться хаотично;
- они должны автоматически выстраиваться в аккуратной рабочей области;
- элементы группировать по видам систем;
- внутри группы размещать строго по вертикали или колонками;
- использовать одинаковые интервалы;
- при добавлении и удалении автоматически перестраивать расположение;
- пользователь должен сразу понимать принадлежность элемента к определённому виду СППЗ.

На экране вывести пояснение:

**«Размещённые объекты доступны к работе без подложки».**

Работа с карточками, журналом, чек-листами, статусами, контекстным меню и другими функциями не должна зависеть от наличия PDF/JPG-подложки.

---

# 2. Восстановить загрузку подложки

Кнопка **«Загрузить подложку»** на вкладке «План» должна снова полноценно работать.

Поддержать уже предусмотренные приложением форматы.

Если подложка загружается после того, как элементы уже были созданы и условно размещены без неё:

1. карточки, журнальные записи, история, статусы и остальные данные сохраняются;
2. условные координаты не считать реальным размещением на новой подложке;
3. ранее созданные элементы перевести в нижнюю/служебную панель;
4. присвоить им состояние отображения:

**«Требует размещения на плане»**;

5. пользователь вручную перетаскивает элементы на реальные места план-схемы;
6. после размещения статус снимается;
7. реальные координаты сохраняются.

---

# 3. Исправить Drag-and-Drop

Проверить и исправить перетаскивание для всех поддерживаемых элементов СППЗ.

Должно работать:

- перетаскивание неразмещённого элемента на подложку;
- изменение позиции уже размещённого элемента;
- сохранение координат;
- сохранение после переключения между вкладками;
- сохранение после перезапуска приложения;
- работа для всех типов СППЗ.

Не считать функцию рабочей, если элемент двигается визуально, но его координаты не сохраняются.

---

# 4. Кнопка и команда «Показать на плане»

Функция должна работать даже без загруженной подложки.

При вызове:

1. перейти в режим «План»;
2. открыть нужный этаж/отметку/узел;
3. найти конкретный элемент;
4. центрировать рабочую область на нём;
5. заметно подсветить выбранный элемент;
6. сохранить уже реализованную удачную логику мигания/пульсации.

Если подложки нет, переход всё равно выполняется к условно размещённому элементу.

---

# 5. Навигация План ↔ Журнал через контекстное меню

## На вкладке «План»

По правой кнопке мыши на элементе добавить:

**«Показать в журнале»**

После выбора:

- открыть вкладку «Журнал»;
- выбрать соответствующий журнал/вид СППЗ;
- найти строку выбранного элемента;
- прокрутить её в видимую область;
- заметно подсветить или кратковременно пульсировать строку.

## На вкладке «Журнал»

По правой кнопке мыши на строке добавить:

**«Показать на плане»**

После выбора:

- перейти на нужный план;
- открыть правильный этаж/отметку;
- центрироваться на элементе;
- подсветить/мигать выбранным элементом.

Навигация должна быть симметричной.

---

# 6. Убрать автоматический переход по обычному клику

Обычный клик по наименованию огнетушителя или другого элемента в журнале **не должен автоматически переводить пользователя на вкладку «План»**.

Переход выполнять только через осознанную команду:

**ПКМ → Показать на плане**

---

# 7. Контекстное меню элемента СППЗ

Контекстное меню должно работать как минимум в:

- режиме «План»;
- режиме «Журнал».

Минимальные команды:

- **Показать в журнале** — для плана;
- **Показать на плане** — для журнала;
- **Снять с эксплуатации**;
- **Переместить**;
- **Заменить**.

Логика операций должна быть общей для всех представлений.

---

# 8. «Снять с эксплуатации»

Не удалять элемент бесследно.

При снятии с эксплуатации:

- изменить эксплуатационный статус;
- сохранить историю элемента;
- сохранить прошлые чек-листы;
- сохранить выполненные работы;
- сохранить связанные документы/фото.

По возможности фиксировать:

- дату;
- причину;
- пользователя;
- комментарий.

---

# 9. «Переместить»

Перемещение должно выполняться только в пределах текущего здания.

При выборе команды:

1. открыть выбор нового допустимого узла данного здания;
2. использовать существующую иерархию дерева;
3. например:

**Здание → Этаж/отметка → Помещение/зона/склад**

4. после выбора показать отдельное подтверждение.

Пример:

**Перемещение элемента**

Элемент будет перемещён:

из: Здание 1 → Этаж 1 → Склад 1  
в: Здание 1 → Этаж 2 → Помещение 215

Также местоположение будет изменено в журнале систем противопожарной защиты.

Кнопки:

- **Переместить**
- **Отмена**

Только после подтверждения выполнить операцию.

После перемещения новое местоположение автоматически обновить во всех связанных представлениях:

- дерево;
- карточка;
- журнал;
- план;
- фильтры;
- отчёты;
- заявки.

Не создавать копию элемента.

Историю перемещений желательно сохранять.

---

# 10. «Заменить»

Команда предназначена для замены существующего элемента новым.

После выбора открыть форму с доступными вариантами:

- тип;
- модель;
- исполнение;
- конкретный новый элемент — в зависимости от текущей структуры приложения.

Сохранить историю старого элемента.

Зафиксировать:

- что было заменено;
- на что;
- дату;
- причину при необходимости.

Новый элемент становится действующим, старый остаётся в истории.

---

# 11. Техническое состояние нового огнетушителя

Исправить текущую логику.

Новый огнетушитель, который пользователь только что внёс в систему, должен **по умолчанию считаться исправным**, если отсутствуют основания считать иначе.

Пример условий:

- выбран изготовитель;
- выбрана марка/модель;
- указана дата изготовления/ввода/размещения по логике карточки;
- заводской номер и другие обязательные поля заполнены;
- срок службы не истёк;
- нет зарегистрированных дефектов;
- нет просроченных обязательных мероприятий;
- история чек-листов пока отсутствует, потому что огнетушитель новый.

В этом случае:

**Техническое состояние = Исправен.**

Отсутствие истории проверок у нового элемента не должно автоматически делать его серым или неисправным.

После проведения проверок состояние определяется по фактическим данным.

---

# 12. Единый источник технического состояния

Сейчас возможна ошибка: карточка показывает «Исправен», а значок на плане остаётся серым.

Исправить.

Техническое состояние должно иметь единый источник и одинаково отображаться:

- в карточке;
- на плане;
- в журнале;
- в правой сводной панели;
- на дашборде;
- в фильтрах;
- в отчётах;
- в заявках.

Цветовая логика:

- **зелёный** — исправен;
- **жёлтый** — требует внимания / приближается срок;
- **красный** — неисправен / просрочено обязательное мероприятие;
- **серый** — недостаточно данных.

---

# 13. Чек-листы огнетушителей

Убрать из отображения непонятные обозначения в скобках:

- «критический»;
- «значительный»;
- аналогичные уровни.

Показывать только понятное название параметра:

- Корпус;
- Покрытие;
- Запорно-пусковое устройство;
- Манометр;
- Маркировка;
- и т. д.

Если внутренние уровни используются в алгоритмах, можно оставить их в данных, но не показывать пользователю без необходимости.

---

# 14. Сторонние организации

Формулировку:

**«Работы выполнены лицензированной сторонней организацией»**

заменить на:

**«Работы выполнены сторонней организацией».**

Поле лицензии сделать необязательным и подписать, например:

**«Лицензия (при наличии / если требуется для данного вида работ)».**

Отсутствие лицензии не должно блокировать сохранение работы, если конкретная операция её не требует.

---

# 15. Фото и файлы в чек-листах

Если пользователь выбирает:

**«Выполнено с замечаниями»**

рядом с полем описания замечания/дефекта добавить:

**«Добавить фото / файл»**

На ПК:

- выбор файла с устройства.

На мобильной версии:

- выбор существующего изображения;
- съёмка камерой.

Вложения должны быть связаны именно с:

**элемент → конкретная проверка → конкретный пункт чек-листа → конкретное замечание**

Не хранить их как несвязанные файлы.

---

# 16. Исправить все поля ручного ввода

Проверить все карточки и формы.

Сейчас часть полей не получает фокус и не позволяет вводить данные, например заводской номер огнетушителя.

Все поля ручного ввода должны:

- получать фокус;
- позволять поставить курсор;
- принимать текст;
- позволять редактирование;
- сохранять данные;
- показывать сохранённое значение при повторном открытии.

Проверить все типы СППЗ.

---

# 17. Исправить поля чек-листов

Проверить все текстовые поля:

- ФИО;
- примечание;
- описание дефекта;
- описание замечания;
- сведения об организации;
- номера документов;
- результаты;
- комментарии;
- другие поля ручного ввода.

Если поле предназначено для пользователя, оно должно быть реально активным.

---

# 18. Убрать «Код системы» из интерфейса

Не показывать пользователю внутренние значения типа:

- «Код системы 01»;
- «Код системы 03.1».

Если они нужны БД или внутренней логике, оставить только во внутренней модели.

Интерфейс должен показывать понятные названия систем.

---

# 19. Полностью переработать назначение правой панели

Правая панель должна иметь три основных режима:

1. **Обзор систем текущего объекта** — основной режим.
2. **Карточка выбранного элемента**.
3. **Библиотека элементов / добавление**.

Добавление элементов — не основная повседневная операция, поэтому библиотека не должна постоянно занимать правую панель.

---

# 20. Основной режим правой панели — сводка

Если конкретный элемент не выбран, правая панель показывает сводку по текущей области:

- здание;
- этаж;
- отметка;
- план;
- другой выбранный узел.

Пример:

**Системы объекта — 1 этаж**

**Огнетушители — 18**
- ОП-4 — 6
- ОП-5 — 4
- ОП-8 — 5
- ОУ-5 — 3

**Пожарные краны — 6**

**Пожарные извещатели — 24**
- дымовые — 16
- ручные — 8

и т. д.

Количество должно рассчитываться автоматически по фактически существующим элементам.

Не хранить вручную введённые итоговые числа.

---

# 21. Общее количество и детализация

Для каждой группы показывать:

- общее количество;
- количество по типам;
- при необходимости по моделям.

Группы должны раскрываться/сворачиваться, чтобы панель не была перегружена.

---

# 22. Перенести фильтры отображения из нижней панели вправо

Существующая нижняя панель фильтрации по типам СППЗ должна быть перенесена в правую сводную панель.

Пример:

**Внутренние системы**

☑ Огнетушители — 18  
☑ Пожарные краны — 6  
☑ Противопожарные двери — 12  
☑ Самоспасатели — 30

**Пожарная автоматика**

☑ Дымовые извещатели — 24  
☑ Ручные извещатели — 7  
☑ СОУЭ — 14  
☑ Клапаны — 8

Чекбоксы включают/выключают отображение соответствующих элементов:

- на плане;
- в журнале;

в зависимости от активного режима.

Количество должно оставаться видно.

---

# 23. Интерактивность сводной панели

Рекомендуемая логика:

- чекбокс — включить/выключить отображение;
- клик по группе — раскрыть детализацию;
- клик по конкретному типу/модели — временно отфильтровать план или журнал по этому типу;
- повторное действие — снять фильтр.

Использовать единый механизм фильтрации, а не отдельные независимые фильтры для плана и журнала.

---

# 24. Сводка должна учитывать уровень дерева

Если выбран:

## Этаж
Показывать элементы данного этажа.

## Отметка
Показывать элементы данной отметки.

## План
Показывать элементы данного плана.

## Здание
Показывать агрегированные данные всего здания.

---

# 25. Разделение систем для здания

На уровне здания показывать три крупных раздела:

## Снаружи здания

Например:

- пожарные гидранты;
- наружные пожарные лестницы;
- наружное противопожарное водоснабжение;
- другие наружные системы.

## Внутри здания

Например:

- огнетушители;
- пожарные краны;
- противопожарные двери;
- самоспасатели;
- другие внутренние элементы.

## Системы пожарной автоматики

Отдельным крупным блоком:

- СПС;
- АУПТ;
- СОУЭ;
- противодымная вентиляция;
- исполнительные устройства;
- связанные элементы автоматики.

---

# 26. Разделение для этажей, отметок и планов

На этих уровнях минимум два крупных раздела:

- **Внутренние системы противопожарной защиты**
- **Системы пожарной автоматики**

Не смешивать пожарную автоматику с огнетушителями и пожарными кранами.

---

# 27. Кнопка «Библиотека элементов»

В верхней части правой панели оставить кнопку:

**«Библиотека элементов»**

При нажатии панель переключается в режим добавления.

После добавления пользователь может вернуться к сводке.

Основная логика:

- ничего не выбрано → сводка;
- выбран элемент → карточка;
- нажата «Библиотека элементов» → добавление;
- выбор снят → снова сводка.

---

# 28. Карточка элемента имеет приоритет

Если пользователь нажал на конкретный элемент, правая панель показывает его карточку.

После снятия выбора автоматически возвращается сводка текущего объекта.

---

# 29. Системы пожарной автоматики — не отдельные несвязанные значки

Пожарная автоматика должна быть реализована как связанная структура.

Не считать независимыми друг от друга:

- дымовые извещатели;
- тепловые извещатели;
- ручные пожарные извещатели;
- СОУЭ;
- клапаны;
- вентиляторы;
- модули пожаротушения;
- исполнительные устройства;
- другие устройства автоматики.

Они должны принадлежать конкретной логической системе.

---

# 30. Головной прибор системы

Главным элементом соответствующей системы должен быть головной прибор:

- ППКУ;
- ППКП;
- прибор управления;
- другой соответствующий прибор в зависимости от типа системы.

При попытке разместить устройство автоматики приложение должно проверить наличие подходящей созданной системы.

Если система/головной прибор отсутствует, показать предупреждение:

**«Не создана система пожарной автоматики. Для размещения данного элемента сначала необходимо создать головной прибор соответствующей системы.»**

Кнопки:

- **Создать прибор**
- **Отмена**

---

# 31. Карточка головного прибора

Минимально предусмотреть:

- наименование;
- тип;
- изготовитель;
- модель/марка;
- заводской номер;
- внутреннее обозначение при необходимости;
- дата выпуска;
- дата ввода в эксплуатацию;
- место установки;
- обслуживаемая система;
- техническое состояние;
- другие необходимые характеристики.

---

# 32. Создать сущность «Система пожарной автоматики»

При создании головного прибора должна создаваться логическая сущность системы.

Пример:

**СПС-1**

Головной прибор:

**ППКУ №1**

Связанные элементы:

- дымовые извещатели — 48;
- тепловые — 12;
- ИПР — 8;
- модули — 4;
- устройства управления — 3.

База должна понимать не только тип устройства, но и его принадлежность к конкретной системе.

---

# 33. Обязательная привязка нового устройства автоматики

При создании нового устройства определить, к какой системе оно относится.

Если подходящая система одна — можно подставить автоматически.

Если несколько — пользователь выбирает.

Пример:

**Относится к системе:**

- СПС-1 — ППКУ №1
- СПС-2 — ППКУ №2

Не допускать постоянного существования устройств автоматики без системной принадлежности, кроме специально предусмотренного временного статуса при импорте.

---

# 34. Физическое местоположение и системная принадлежность — разные связи

Головной прибор является логическим центром, но не координатным родителем.

Например:

Извещатель физически расположен:

**Здание 1 → Этаж 3 → Помещение 312**

При этом относится к:

**СПС-1 → ППКУ №1**

Эти связи должны храниться независимо.

Устройства одной системы могут находиться на разных этажах.

---

# 35. Иерархия пожарной автоматики

Модель должна позволять развитие структуры примерно так:

**Здание**
→ **Система пожарной автоматики**
→ **Головной прибор**
→ **Линия / шлейф / зона / интерфейс**
→ **Подключённые элементы**
→ **Исполнительные устройства**

Не обязательно сразу показывать пользователю всю глубину структуры, но база данных должна позволять развивать это дальше без полной переделки.

---

# 36. Двусторонние связи пожарной автоматики

В карточке извещателя показывать:

- систему;
- головной прибор.

Ссылки должны быть интерактивными.

Из карточки устройства можно открыть головной прибор.

В карточке головного прибора показывать связанные устройства и количество по типам.

Пример:

**Подключено элементов: 74**

- дымовые — 48;
- тепловые — 12;
- ручные — 8;
- модули — 6.

Связь работает:

**головной прибор → устройства**

и

**устройство → система / головной прибор**

---

# 37. Отображение пожарной автоматики в правой панели

Показывать структурированно.

Пример:

## Пожарная автоматика

### СПС-1 — ППКУ №1
- дымовые — 48
- тепловые — 12
- ИПР — 8

### СПС-2 — ППКУ №2
- дымовые — 32
- ИПР — 6

### СОУЭ-1
- речевые оповещатели — 14
- световые указатели — 22

Пользователь должен видеть не только количество, но и принадлежность к системе.

---

# 38. Фильтрация пожарной автоматики

Предусмотреть возможность:

- скрыть всю пожарную автоматику;
- показать только СПС;
- только СОУЭ;
- только АУПТ;
- только противодымную вентиляцию;
- конкретную систему;
- конкретный тип устройств;
- при необходимости элементы конкретного головного прибора.

---

# 39. Архитектура пожарной автоматики

Не создавать отдельные дублирующие таблицы под план, журнал и карточку.

Использовать нормализованную модель.

Возможный принцип:

- `automation_system` — логическая система;
- существующая сущность `sppz_element` / `device` — конкретный физический элемент;
- ссылка `automation_system_id`;
- при необходимости `parent_device_id`;
- в дальнейшем `loop_id`, `zone_id` и т. п.

Конкретные имена и миграции определить после анализа текущей БД.

---

# 40. Предусмотреть развитие автоматики

Архитектура должна позволять позднее добавить:

- адреса устройств;
- шлейфы;
- зоны;
- линии связи;
- интерфейсные модули;
- зависимости управления;
- сценарии событие → действие;
- связи СПС с СОУЭ;
- связи СПС с противодымной вентиляцией;
- запуск АУПТ;
- управление клапанами;
- управление вентиляторами.

На текущем этапе не обязательно реализовывать весь этот функционал в UI, но структура данных не должна мешать его развитию.

---

# 41. Конструктор заявок

Кнопка **«Заявка»** должна открывать универсальный конструктор заявки.

Он должен адаптироваться к выбранному виду СППЗ.

Для огнетушителей предусмотреть, например:

- перезарядку;
- техническое обслуживание;
- гидравлические испытания;
- периодические проверки;
- ежеквартальные осмотры;
- ежегодные осмотры;
- устранение замечаний;
- другие мероприятия из соответствующих чек-листов.

Не создавать отдельную жёсткую форму только под огнетушители.

По возможности список мероприятий получать из конфигурации/чек-листов конкретной системы.

---

# 42. Период заявки

Для мероприятий, связанных со сроками, пользователь задаёт период.

Например:

**Включить огнетушители, срок перезарядки которых заканчивается с [дата] по [дата].**

Аналогично для:

- испытаний;
- осмотров;
- ТО;
- проверок;
- других периодических мероприятий.

После задания условий приложение само подбирает элементы.

---

# 43. Область заявки

Предусмотреть выбор:

- всё здание;
- конкретный этаж/отметка;
- конкретное помещение;
- склад;
- другой существующий дочерний узел.

Если заявка открыта из здания — здание подставляется по умолчанию.

Если из этажа — этаж подставляется по умолчанию.

---

# 44. Автоматический подбор элементов в заявку

После выбора:

- вида системы;
- вида мероприятия;
- периода;
- области;

система автоматически формирует перечень подходящих элементов.

Перед окончательным формированием показать предварительный список.

Пользователь может исключить отдельные позиции.

Принцип:

**тип СППЗ → мероприятие → период/условия → область → автоматический подбор → предварительный просмотр → заявка**

Эта логика должна работать для всех видов СППЗ.

---

# 45. Обязательная сквозная проверка после изменений

После реализации не ограничиваться успешной сборкой.

Необходимо вручную пройти основные пользовательские сценарии.

Минимальный тест:

1. Создать здание и этаж.
2. Не загружать подложку.
3. Добавить несколько огнетушителей и других элементов.
4. Убедиться, что элементы упорядочены по группам.
5. Заполнить карточку нового огнетушителя.
6. Проверить ввод заводского номера и всех текстовых полей.
7. Убедиться, что новый огнетушитель имеет статус «Исправен».
8. Убедиться, что индикатор зелёный.
9. Открыть журнал и проверить тот же элемент.
10. ПКМ → «Показать на плане».
11. Проверить центрирование и мигание.
12. На плане ПКМ → «Показать в журнале».
13. Проверить подсветку строки.
14. Переместить элемент на другой этаж того же здания.
15. Проверить окно подтверждения.
16. Проверить синхронизацию плана, журнала и карточки.
17. Загрузить подложку.
18. Проверить перевод существующих элементов в «Требует размещения на плане».
19. Перетащить элементы на подложку.
20. Проверить сохранение координат.
21. Открыть чек-лист.
22. Проверить все поля ввода.
23. Проверить «Выполнено с замечаниями» и прикрепление фото/файла.
24. Проверить правую сводную панель на уровне этажа.
25. Проверить пересчёт количества на уровне здания.
26. Проверить включение/выключение видов систем.
27. Попробовать добавить дымовой извещатель без головного прибора.
28. Проверить предупреждение.
29. Создать головной прибор.
30. Создать несколько связанных устройств.
31. Проверить связи устройство ↔ система ↔ головной прибор.
32. Создать второй головной прибор и проверить выбор системы.
33. Разместить устройства одной системы на разных этажах.
34. Проверить, что системная принадлежность сохраняется.
35. Проверить конструктор заявки и автоматический подбор элементов.
36. Перезапустить приложение.
37. Проверить сохранность данных, статусов, координат, связей и истории.

Если в ходе проверки обнаружены связанные ошибки текущей реализации, исправить их в рамках этого блока.

---

# 46. Главный итог

После выполнения доработок приложение должно работать как единая связанная система.

Основная логика интерфейса:

- ничего не выбрано → справа сводка текущего объекта;
- выбран элемент → справа его карточка;
- нажата «Библиотека элементов» → режим добавления;
- выбор снят → возврат к сводке;
- План и Журнал связаны через контекстные команды;
- техническое состояние едино во всех представлениях;
- элементы можно полноценно использовать без подложки;
- после загрузки подложки они требуют реального размещения;
- пожарная автоматика представлена как связанные системы с головными приборами;
- заявки формируются конструктором на основании реальных данных и сроков;
- все пользовательские поля должны быть реально доступными для ввода;
- все изменения сохраняются и корректно отображаются после перезапуска.

## Важно

Не выполнять изменения только визуально.

Каждая описанная функция должна реально работать с данными, сохраняться в БД и быть синхронизирована между связанными представлениями приложения.
