## 1. Назначение

Программа ведёт учёт систем противопожарной защиты предприятия: где что установлено, в каком состоянии, когда проверялось и когда проверять снова. План и журнал — два представления одних и тех же данных: объект существует в одной записи, а не в двух копиях.

## 2. Язык

**Весь интерфейс — только на русском языке.** Названия кнопок, вкладок, полей, сообщений об ошибках, отчётов и печатных форм. Английские слова допустимы лишь там, где они являются общепринятым обозначением (форматы файлов PDF, XLSX).

## 3. Структура объекта

### 3.1. Уровни дерева

```
Организация
└── Цех
    └── Здание                    ← ГЕНПЛАН объекта + общий журнал
        │                           + характеристики в части ПБ (часть 4)
        ├── Этаж (отметка)        ← ПОЭТАЖНЫЙ ПЛАН + журнал этажа
        │                           + помещения с категориями (часть 5.5)
        ├── Этаж (отметка)
        └── Склад                 ← окно склада + журнал склада
```

Три правила, которые нарушать нельзя:

1. **Генплан — только на уровне здания.** Поэтажного плана у здания нет.
2. **Поэтажный план — только на уровне этажа.** Генплана у этажа нет.
3. **Склад — узел уровня здания, наравне с этажами.** Внутрь этажа склад не вкладывается.

| Уровень | Что содержит | Рабочая область | Журнал |
|---|---|---|---|
| **Организация** | Цеха | Нет | Сводный по всем цехам |
| **Цех** | Здания | Нет | Сводный по зданиям цеха |
| **Здание** | Этажи и склады; карточка характеристик ПБ | **Генплан объекта** | **Общий журнал здания** — все этажи и все элементы здания |
| **Этаж (отметка)** | Оборудование на плане этажа | Поэтажный план | Только СППЗ данного этажа |
| **Склад** | Оборудование без привязки к плану | Окно склада | Только содержимое склада |

Цех необязателен: здание разрешено заводить прямо в организации.

### 3.2. Раскрытие и скрытие ветвей

Каждый узел, у которого есть вложенные узлы, имеет знак **«+» / «−»** непосредственно на самой строке узла. Нажатие раскрывает или скрывает ветвь. Состояние раскрытия сохраняется между запусками программы.

### 3.3. Склад

Склад — узел того же уровня, что и этаж, но без плана здания. В него пользователь складывает то, что учитывается, но не установлено на месте:

- запасные огнетушители для замены;
- рукава, стволы, головки, порошковые модули из резерва;
- оборудование, снятое на перезарядку или в ремонт;
- **оборудование, числящееся за техникой** — огнетушители на пожарных автомобилях заводятся отдельным складом с названием единицы техники.

Отдельного вида узла «Техника» в программе нет. Это было исключение из общего правила, а исключения в структуре данных не заводятся: техника — частный случай склада.

Склад работает так же, как план: пользователь переносит в окно склада значки оборудования из правой панели, и одновременно с этим появляются записи в журнале учёта. Что в журнале — то и в окне склада.

### 3.4. Включение и отключение в общем журнале

В общем журнале здания пользователь может **отключить показ отдельных этажей и складов**. Отключение влияет только на состав представления и печатных форм; сами записи остаются на месте и продолжают учитываться в сроках.

Пример: запасные огнетушители со склада не нужны в журнале, предъявляемом по конкретному этажу, но нужны в инвентарной ведомости.

## 4. Карточка здания: характеристики в части пожарной безопасности

Характеристики в части ПБ заполняются **только на уровне здания**. У этажа, склада, цеха и организации таких полей нет: степень огнестойкости и класс конструктивной пожарной опасности — свойства здания целиком.

Карточка открывается под деревом сразу после создания здания. Все поля с фиксированным набором значений заполняются **выпадающими списками**, а не вводом текста: от этих значений зависят нормативные требования, и опечатка в них исказит выводы программы.

| Поле | Тип | Значения |
|---|---|---|
| Наименование | текст | — |
| Инвентарный номер | текст | — |
| Классы функциональной пожарной опасности | **список с множественным выбором** | Ф1.1, Ф1.2, Ф1.3, Ф1.4, Ф2.1–Ф2.4, Ф3.1–Ф3.7, Ф4.1–Ф4.4, Ф5.1, Ф5.2, Ф5.3 |
| Степень огнестойкости | список | I, II, III, IV, V |
| Класс конструктивной пожарной опасности | список | С0, С1, С2, С3 |
| Этажность (надземных этажей) | число | — |
| Подземных этажей | число | — |
| Высота здания, м | число | — |
| Площадь застройки, м² | число | — |
| Строительный объём, м³ | число | — |
| Категория здания по взрывопожарной опасности | список | **А, Б, В, Г, Д, не категорируется** |
| Основание категории | текст | документ, которым определена категория |
| Тип системы оповещения (СОУЭ) | список | 1, 2, 3, 4, 5, не требуется |
| Автоматическая пожарная сигнализация | список | есть, нет, не требуется |
| Автоматическая установка пожаротушения | список | нет, водяная, пенная, газовая, порошковая, аэрозольная, тонкораспылённая вода |
| Внутренний противопожарный водопровод | список | есть, нет, не требуется |
| Противодымная защита | список | есть, нет, не требуется |
| Тип лестничных клеток | список | обычные, Н1, Н2, Н3, не применимо |
| Количество эвакуационных выходов | число | — |
| Год постройки | число | — |
| Ответственный за пожарную безопасность | текст | до появления справочника лиц |

Два уточнения, которые часто путают:

- **Здание может совмещать несколько функциональных назначений** — например, административная часть Ф4.3 и производственная Ф5.1. Поэтому поле допускает несколько значений: они выбираются из списка и хранятся в одном поле через запятую.
- **Категория В1–В4 к зданию не применяется.** По СП 12.13130 на классы В1–В4 делятся только **помещения**; здание в целом относится к категории **А, Б, В, Г или Д**. Поэтому В1–В4 есть в карточке помещения (часть 5.5) и отсутствуют в карточке здания.

Значения списков — данные, а не перечисления в коде: при изменении нормативной базы они правятся без пересборки программы.

Незаполненные характеристики не блокируют работу, но здание помечается как «характеристики не заполнены» и попадает в дашборд состояния: без них нормативные выводы неполны.

## 5. Рабочая область (центральная панель)

Центр имеет две вкладки: **План** и **Журнал**. Их содержимое зависит от выбранного уровня дерева.

### 5.1. Генплан объекта — уровень «Здание»

Вместо поэтажного плана на уровне здания ведётся генплан: здание и прилегающая территория. На него наносятся:

- пожарные гидранты;
- пожарные водоёмы, резервуары, водонапорные башни, артскважины;
- пирсы и площадки для установки пожарной техники на водоисточник;
- **места подключения пожарной техники** — патрубки для подключения к внутреннему водопроводу и к установкам пожаротушения;
- наружные пожарные лестницы;
- ограждения кровли;
- пожарные проезды и площадки для спецтехники, места разворота;
- въезды на территорию, шлагбаумы, ворота;
- наружные пожарные шкафы и щиты, места хранения пожарного инструмента;
- пожарный пост, помещение дежурного;
- места сбора людей при эвакуации;
- сухотрубы и их выводы наружу;
- насосные станции.

### 5.2. Поэтажный план — уровень «Этаж (отметка)»

На поэтажный план наносятся системы противопожарной защиты этажа:

- огнетушители и первичные средства;
- пожарные краны и шкафы ВПВ;
- извещатели пожарные: дымовые, тепловые, пламени, аспирационные, линейные, ручные;
- приборы приёмно-контрольные, модули ввода-вывода, источники бесперебойного питания;
- оповещатели СОУЭ, приборы управления;
- клапаны и вентиляторы противодымной защиты;
- оросители, узлы управления, модули порошкового и газового пожаротушения;
- противопожарные двери, люки, шторы, экраны;
- эвакуационные выходы, лестничные клетки;
- средства индивидуальной защиты, самоспасатели;
- планы эвакуации и знаки пожарной безопасности.

### 5.3. Окно склада — уровень «Склад»

Свободное поле, куда переносятся значки оборудования. Координаты значения не имеют: важен состав, а не расположение. Каждый перенесённый значок создаёт запись в журнале склада.

### 5.4. Загрузка подложки

На вкладке «План» для уровня без загруженной подложки показывается **кнопка «Загрузить подложку» и поле для перетаскивания файла**. После выбора или перетаскивания открывается отдельная вкладка подготовки подложки: выбор страницы, разрешение, поворот, очистка, задание масштаба. По завершении подложка привязывается к тому узлу, откуда её загружали.

Поддерживаемые форматы: SVG, PDF, PNG, JPG, DXF. Автоматическое распознавание планов в объём не входит (решение заказчика): подложки готовятся вручную, предпочтительно в векторном виде.

### 5.5. Помещения на этаже

Помещения ведутся **на уровне этажа** и нигде больше. В карточке узла-этажа есть список помещений и кнопка **«+ Добавить помещение»**.

У помещения заполняются:

| Поле | Тип | Значения |
|---|---|---|
| Наименование | текст | например, «Электрощитовая» |
| Номер | текст | номер по экспликации |
| Категория по взрывопожарной опасности | список | **А, Б, В1, В2, В3, В4, Г, Д, не категорируется** |
| Документ-основание категории | текст | расчёт категорий, проект |
| Площадь | вычисляется | из обводки на плане |
| Высота, м | число | нужна для правил размещения извещателей |

Рядом с каждым помещением — кнопка **«Отметить на плане»**. Она включает режим обводки:

1. пользователь ставит точки по углам помещения; линия тянется за курсором;
2. фигура замыкается двойным щелчком или нажатием на первую точку — это **любой замкнутый многоугольник**, а не только прямоугольник;
3. область заливается **полупрозрачным цветом**, чтобы под ней оставался виден чертёж;
4. **площадь считается автоматически** по обводке и масштабу плана и записывается в карточку помещения. Пользователь площадь не набирает;
5. обводку можно перерисовать заново; предыдущая заменяется.

Цвет заливки зависит от категории — так на плане сразу видно, где взрывопожароопасные помещения. Показ заливки включается и выключается слоем «Помещения».

Если у этажа не задан масштаб плана, обводка выполняется, но площадь не вычисляется, и программа прямо сообщает: сначала задайте масштаб.

Площадь помещения и его категория дальше используются правилами: например, огнетушители в помещениях категории А проверяются не реже одного раза в 6 месяцев, а не раз в год.

### 5.6. Вкладка «Журнал»

Показывает записи выбранного уровня по правилам части 3.1. На вкладке есть **кнопка «Перенести существующий журнал» и поле для перетаскивания файла** — см. часть 8.

## 6. Правая панель — библиотека элементов

### 6.1. Наборы значков по уровням

Состав панели зависит от выбранного уровня:

| Уровень | Набор значков |
|---|---|
| Здание (генплан) | Гидранты, водоёмы и резервуары, пирсы, места подключения пожарной техники, наружные лестницы, ограждения кровли, проезды и площадки, наружные шкафы, пожарный пост, места сбора |
| Этаж | Огнетушители, краны ВПВ, извещатели, приборы, оповещатели, клапаны и вентиляторы ПДЗ, оросители и модули АУП, противопожарные двери и люки, эвакуационные выходы, знаки и планы эвакуации |
| Склад | Тот же набор, что и для этажа: на складе может лежать любое оборудование |

Каждый значок сопровождается названием, чтобы пользователь не разгадывал условные обозначения.

### 6.2. Размещение

Элемент переносится на план перетаскиванием. Точка установки — место, куда его отпустили; дальше её можно двигать.

### 6.3. Групповое создание

Правой кнопкой по элементу библиотеки открывается окно **«Создать несколько»**:

1. количество;
2. общие характеристики: марка и модель, изготовитель, дата ввода в эксплуатацию, срок службы, ответственный, помещение;
3. **схема нумерации**: префикс, начальный номер, шаг. Например, префикс «ОП-», начальный номер 15, шаг 1 даёт ОП-15, ОП-16, ОП-17. Программа заранее показывает список номеров, которые получатся, и предупреждает, если такие номера уже заняты;
4. способ размещения — один из трёх:
   - **по щелчку**: программа переходит в режим расстановки, каждый щелчок по плану ставит следующий по номеру объект, счётчик показывает, сколько осталось;
   - **в помещение**: все объекты создаются внутри указанного помещения с автоматической расстановкой у стен, как на планах эвакуации, с последующим ручным исправлением;
   - **без размещения**: объекты создаются в журнале со статусом «Требует размещения» и расставляются позже. Для склада это единственный способ.

Отменить групповое создание можно одним действием, пока не подтверждено размещение.

### 6.4. Сворачивание панели

Панель **сворачивается** кнопкой, чтобы после расстановки оборудования освободить место под план. Состояние сохраняется между запусками.

### 6.5. Два режима правой панели

Правая панель работает в двух режимах и переключается между ними сама:

| Режим | Когда показывается | Что в нём |
|---|---|---|
| **Библиотека** | Ничего не выбрано на плане | Значки элементов для текущего уровня; перетаскивание на план; групповое создание правой кнопкой |
| **Карточка объекта** | Пользователь щёлкнул объект на плане | Карточка выбранного объекта: тип, учётный номер, характеристики, состояние, действия |

Переключение обратно к библиотеке — щелчком по пустому месту плана или кнопкой «к библиотеке» в карточке. Два режима не показываются одновременно: панель одна, и делить её пополам значит сделать неудобными оба.

### 6.6. Перетаскивание в обе стороны

- **Из панели на план** — создаёт объект: одновременно появляется значок на плане и запись в журнале.
- **С плана в панель** — **снимает объект с плана**: значок исчезает, а запись в журнале остаётся со статусом «Требует размещения». Это не удаление: журнал предъявляется при проверке, и данные из него не пропадают.
- **По плану** — перемещает объект в другое место.

Полное исключение объекта из учёта — только вывод из эксплуатации в его карточке, с сохранением истории.

## 7. Объекты СППЗ на плане

### 7.1. Объект и запись журнала — одно и то же

Перетаскивание значка из библиотеки создаёт **одну запись**: она же значок на плане и она же строка журнала. Отдельной таблицы объектов у плана нет, поэтому расхождение между планом и журналом невозможно по устройству, а не по дисциплине.

Объект принадлежит тому же узлу, на плане которого создан: генплан — объекты здания, поэтажный план — объекты этажа, склад — объекты склада (без координат).

### 7.2. Карточка объекта

Открывается в правой панели по щелчку на значке.

| Поле | Тип | Примечание |
|---|---|---|
| Тип | из библиотеки | не меняется: другой тип — другой объект |
| Учётный номер | текст | инвентарный или заводской номер, по которому объект знают на предприятии |
| Марка, модель | текст | например, ОП-5(з) АВСЕ |
| Изготовитель | текст | — |
| Заводской номер | текст | — |
| Дата ввода в эксплуатацию | дата | от неё считаются сроки |
| Срок службы, мес | число | для контроля истечения |
| Помещение | список | выбирается из помещений этажа |
| Техническое состояние | список | исправен, неисправен, требует ремонта, не определено |
| Примечание | текст | — |

Из карточки доступны: показать в журнале, снять с плана, вывести из эксплуатации.

Техническое состояние ставит человек по результату работы. Регламентный статус (норма, приближается срок, просрочено) вычисляется движком и в карточке только показывается — вручную он не правится.

### 7.3. Объекты, ожидающие размещения

**Объект можно завести до того, как появился план.** Пока подложка не загружена, элементы из правой панели переносятся в рабочую область как обычно: они выстраиваются **строкой снизу** и ждут плана. Строка подписана: «Требуют размещения на плане».

Та же строка наполняется сама:

- когда журнал заполнен переносом из Excel — у импортированных записей координат нет;
- когда объект сняли с плана перетаскиванием в правую панель;
- когда план заменили и часть объектов оказалась вне нового чертежа.

Как только план загружен, объект из этой строки перетаскивается на своё место. Обратное перетаскивание — с плана в строку — возвращает его в ожидающие.

Счётчик ожидающих виден постоянно, пока не станет нулевым. Это прямое следствие требования ТЗ: объект типа «обязательно размещается» без координат — незакрытая работа, а не норма.

Исключение — склад: там координат нет по существу, и его содержимое в строку ожидающих не попадает.

### 7.4. Строгое соответствие журнала и графики

**Что в журнале — то и на плане, и наоборот.** Это не пожелание, а устройство программы:

- запись одна: значок на плане и строка журнала читаются из неё же, второй копии не существует;
- объект, созданный на плане, появляется в журнале в тот же момент, без отдельного действия;
- объект, заведённый в журнале или пришедший импортом, немедленно виден во вкладке «План» — в строке ожидающих размещения;
- снятие с плана не удаляет запись из журнала, а удаление из журнала невозможно: только вывод из эксплуатации, и тогда объект исчезает и с плана, и из действующего журнала одновременно.

Расхождение между планом и журналом в такой схеме невозможно, потому что синхронизировать нечего.

### 7.5. Что объект не делает

Объект не хранит нормативных сроков: они вычисляются по типу, характеристикам и пакету правил. В карточке показывается результат расчёта со ссылкой на пункт документа, а не введённая руками дата следующей проверки.

## 8. Журналы

| Журнал | Где открывается | Состав |
|---|---|---|
| Сводный по организации | Уровень «Организация» | Все цеха и здания |
| Сводный по цеху | Уровень «Цех» | Все здания цеха |
| Общий журнал здания | Уровень «Здание» | Элементы генплана, все этажи, все склады. Этажи и склады можно отключать из показа |
| Журнал этажа | Уровень «Этаж» | Только СППЗ этого этажа |
| Журнал склада | Уровень «Склад» | Только содержимое склада |

Журнал ведётся вкладками по типам оборудования; состав колонок настраивается. Любая запись открывается двумя способами — из журнала «показать на плане» и с плана «показать в журнале».

## 9. Перенос существующих журналов

Организация уже ведёт учёт в Excel или в другом формате. Программа обязана принять эти данные, а не требовать ввода заново.

Порядок:

1. на вкладке «Журнал» пользователь нажимает «Перенести существующий журнал» или перетаскивает файл;
2. открывается отдельная вкладка переноса: выбор листа, автоматическое определение строки заголовков, отсечение служебных блоков и подсказок;
3. **согласование переноса**: слева колонки исходного файла, справа поля формы программы; программа предлагает сопоставление, пользователь подтверждает или исправляет;
4. правила преобразования: даты Excel в календарные даты, распознавание значений вроде «дата не верна», нормализация обозначений типа «ОВЭ-5 (Бонтел)»;
5. предпросмотр с отчётом: сколько записей будет создано, сколько строк с ошибками и какими, есть ли дубликаты учётных номеров;
6. подтверждение — записи создаются одной операцией. Импортированные объекты получают статус «Требует размещения», пока не нанесены на план.

Отчёт о переносе сохраняется: при проверке должно быть видно, откуда взялись данные.

## 10. Дашборд состояния объекта и отчёты

Отдельная вкладка верхнего уровня.

### 10.1. Состояние объекта защиты

Наглядная сводка, обновляемая автоматически:

- доля исправного оборудования, количество неисправного и требующего ремонта;
- **просроченные проверки** — количество и перечень, с переходом к записи;
- ближайшие сроки: 7 дней, 30 дней, 90 дней;
- объекты со статусом «Требует размещения»;
- временно отключённые системы и зоны, с датами отключения;
- открытые дефекты по критичности;
- здания с незаполненными характеристиками ПБ;
- оборудование с истекающим сроком службы;
- разрез по зданиям, этажам и системам — чтобы видеть, где именно неблагополучно.

### 10.2. Отчёты и документы

Формирование в один выбор:

- журналы эксплуатации по формам ППР РФ №1479 (по пунктам 60, 48, 50, 52, 54, 42, 43/124, 13, 17, 30);
- ведомость технического обслуживания за период;
- **заявки**: на перезарядку огнетушителей, на замену оборудования с истёкшим сроком службы, на устранение дефектов, на проведение испытаний;
- акт проверки работоспособности систем;
- годовой план-график проверок и обслуживания;
- инвентарная ведомость по зданию, этажу, складу;
- перечень просроченного и неисправного оборудования;
- выгрузка в XLSX и PDF, печать на A4 и A3.

Каждый отчёт содержит основание: пункт нормативного документа, по которому назначен срок.

## 11. Общие требования к интерфейсу

Оформление (цвета, шрифты, значки) — рабочее и будет заменено позже. Требования ниже относятся к устройству экрана, а не к его внешнему виду, и при смене оформления сохраняются.

### 11.1. Верхнее меню

Только два раздела: **«Главный экран»** и **«Дашборд и отчёты»**. Отдельных вкладок для подложки и для импорта плана в меню нет.

Подготовка подложки — не раздел программы, а шаг работы: она открывается сама после того, как пользователь загрузил файл в рабочую область узла, и закрывается по завершении, возвращая на главный экран. Пользователь не должен помнить, в какой вкладке лежит инструмент: он работает с узлом, а инструменты приходят к нему.

Формат файла плана — тот же, что принимает подложка: SVG, PDF, PNG, JPG.

### 11.2. Левое поле

Дерево объекта занимает **всё левое поле целиком**: это основной инструмент навигации, и он не должен ужиматься ради того, что нужно изредка.

Карточка выбранного узла **свёрнута по умолчанию** и раскрывается кнопкой со стрелкой внизу поля. Раскрытая карточка занимает нижнюю часть поля; состояние запоминается между запусками.

### 11.3. Правое поле

Библиотека элементов и карточка объекта — два режима одной панели, см. часть 6.5.

1. Три поля рабочего экрана: слева дерево и управление им, в центре план и журнал, справа библиотека элементов.
2. Все действия над структурой — в левом поле; пользователь не ищет, где что создаётся.
3. Подпись схемы собирается из дерева и показывается над рабочей областью; она же попадает в штамп печатного плана.
4. Пользователь никогда не считает даты сам.
5. Массовые операции обязательны во всех списках.
6. Понятные сообщения об ошибках: что произошло, почему и что сделать.
7. Пустые состояния объясняют, что делать дальше.

## 12. Что в объём не входит

- Автоматическое распознавание планов (отложено решением заказчика; подложки готовятся вручную).
- Отдельная сущность «Техника» — заменена складом.
- Расчёт категорий помещений по СП 12.13130 — категория вводится с указанием документа-основания.
- Автоматический вердикт о необходимости систем защиты — только справка с цитатами.

## Д1. Главный принцип: однократный ввод — многократное использование

Программа не является электронной копией бумажного журнала. Пользователь выполняет фактическую проверку и вводит **только то, что увидел или измерил**. Идентификаторы, объект, место, система, норматив, периодичность, следующая дата, статус, запись в общий журнал, история и связи с документами формируются программой.

Этот принцип имеет приоритет при любом расхождении в требованиях к интерфейсу: если поле можно вычислить или подставить — оно не запрашивается у человека.

## Д2. Сущность «Система СППЗ»

Прежние части ТЗ вели цепочку «здание → этаж → помещение → оборудование». Дополнение вводит недостающее звено:

```
Организация → Здание → Этаж (отметка) → Помещение → СИСТЕМА → Оборудование
```

**Система** — учётная единица уровня здания: СПС, ВПВ, СОУЭ, АУПТ, противодымная вентиляция, наружное водоснабжение и так далее. У системы есть класс, номер, защищаемая зона, проект, обслуживающая организация и договор. Оборудование принадлежит системе; для первичных средств, огнезащиты и документации на месте принадлежность необязательна.

Система нужна для того, что через оборудование не выражается: комплексные испытания, отключения целиком, взаимодействие СПС → СОУЭ → АУПТ → противодымная защита.

## Д3. Разделы журнала

Вкладки журнала группируются не только по типам оборудования (часть 8), но и по разделам:

| Раздел | Состав |
|---|---|
| **Общий журнал** | Автоматически формируемая хронологическая лента всех событий эксплуатации |
| **Наружные средства и сооружения** | Гидранты, наружное водоснабжение, пожарные лестницы, ограждения кровли, прочие наружные средства |
| **Внутренние системы и средства** | ВПВ, огнетушители, противопожарные двери, ворота и люки, огнезащита, занавесы, щиты и инвентарь |
| **Пожарная автоматика** | СПС, АУПТ, СОУЭ, противодымная вентиляция, взаимодействие систем |
| **Служебные** | Ремонт, испытания, документы |

Уровень дерева задаёт **область видимости** записей (часть 8), разделы задают **вкладки внутри неё**. Это две независимые оси, а не противоречие.

## Д4. Общий журнал — лента событий

Общий журнал **не заполняется руками**: он собирается из выполненных мероприятий. Двойного ввода не существует — запись в специализированной вкладке и строка общего журнала это одно и то же событие.

| Поле | Откуда | Ручной ввод |
|---|---|---|
| Дата | автоматически | нет |
| Система | из контекста записи | нет |
| Объект, зона | из карточки | нет |
| Вид мероприятия | из выбранной операции | выбор |
| Оборудование | из карточки | нет |
| Результат | фактический | выбор из списка |
| Дефект | фактически, при наличии | да |
| Принятые меры | по результату | выбор |
| Исполнитель | из учётной записи | нет |
| Следующая проверка | расчёт по регламенту | нет |
| Статус | расчёт | нет |
| Документ | связь с файлом | нет |

## Д5. Мероприятие — отдельное событие, а не правка карточки

У карточки оборудования **одна история**, сколько бы проверок ни прошло. Проверка добавляет событие, а не перезаписывает карточку. Это уже заложено в модель (объект и запись журнала — одна сущность, часть 7.1), и дополнение это закрепляет: **проверки хранятся отдельной лентой мероприятий, привязанной к оборудованию.**

## Д6. Единица отображения специализированного журнала

Это требование задаёт **устройство таблицы** специализированной вкладки журнала (часть 8, раздел Д3) и напрямую определяет, как её строить в коде.

**Единица отображения — конкретное оборудование, одна строка.** Не мероприятие, не событие: строка таблицы — это огнетушитель, извещатель, кран ВПВ как учётная единица. Событий и мероприятий у одной строки может быть много, самой строки — одна, ровно как одна карточка оборудования (Д5).

**Набор мероприятий формируется автоматически** — по типу оборудования и применимым правилам, а не выбирается пользователем. Для огнетушителя это, например, осмотр и перезарядка; для клапана противодымной защиты — контроль функционирования и испытание. Состав набора — результат применения пакета правил к типу и характеристикам оборудования (документ 00, П3–П4), а не свойство, которое вводится в карточке.

У каждого мероприятия в строке — свои независимые данные:

| Свойство | Источник |
|---|---|
| Периодичность | пакет правил, по типу оборудования и условиям применимости |
| Дата последнего выполнения | из ленты истории мероприятия |
| Следующая плановая дата | расчёт по периодичности и дате последнего выполнения |
| Статус | расчёт (Д11): норма, скоро, просрочено, неисправно, на ремонте, не эксплуатируется, нет данных |

**Отображение — колонка на каждый вид мероприятия.** Строка оборудования пересекается с колонками мероприятий, и на пересечении — ячейка с датой и статусом (цветом по Д11). Так одной строкой видно сразу всё: что с этим огнетушителем происходит по каждому виду работ, какие сроки подходят, что просрочено.

**Ячейка мероприятия — вход в чек-лист и историю.** Щелчок на ячейке открывает:

1. чек-лист для этого вида работ (Д8) — с него же начинается сценарий проведения проверки (Д7);
2. историю выполнения именно этого мероприятия для этого оборудования — прошлые даты, результаты, исполнителей, документы.

Мероприятие без выполненной ни разу работы показывается пустой ячейкой со статусом «нет данных», а не отсутствующей колонкой: применимость мероприятия к оборудованию не зависит от того, выполнялось ли оно уже. Пустая ячейка — рабочее задание, а не ошибка отображения.

## Д7. Сценарий проведения проверки

1. Пользователь открывает узел или список предстоящих мероприятий.
2. Открывает карточку оборудования.
3. Нажимает «Провести проверку», «Провести ТО» или «Провести испытание».
4. Программа показывает **готовый чек-лист** именно для этой системы и этого вида работ.
5. Пользователь вводит только фактическое: состояние, измеренные параметры, наличие дефекта, при необходимости фото и комментарий. Результаты вида «исправно / неисправно», «да / нет», «соответствует / не соответствует» выбираются, а не набираются.
6. После сохранения программа создаёт запись в общем журнале, рассчитывает следующую дату, статус и контрольный срок.
7. При неисправности программа предлагает создать запись в разделе «Ремонт», связанную с этой проверкой.
8. Приложенные фото, акт или протокол связываются с оборудованием и с событием автоматически.

## Д8. Чек-листы вместо свободного заполнения

Для каждого вида работ — заранее подготовленный нормативно-ориентированный чек-лист. Пользователь его не составляет.

- **ВПВ:** комплектность шкафа, клапан, рукав, ствол, пломба, давление, водоотдача.
- **СПС:** ППКП, извещатели, линии связи, резервное питание, взаимодействие с другими системами.
- **Огнетушители:** пломба, манометр, масса, корпус, раструб, срок перезарядки.

Чек-листы — **данные, а не код**: они лежат в пакете правил рядом с периодичностями и обновляются вместе с нормативной базой.

Если пункт отмечен «неисправно», автоматически открываются дополнительные поля: описание дефекта, фото, принятые меры, необходимость ремонта.

## Д9. Классификация полей

| Категория | Примеры | Ввод пользователем |
|---|---|---|
| Автоматические | идентификатор, дата и время, объект, система, исполнитель, норматив, периодичность | нет |
| Выпадающие | тип, результат, состояние, вид мероприятия, статус ремонта | выбор |
| Расчётные | следующая дата, просрочка, количество дней, статус | нет |
| Фактические | показание прибора, состояние, дефект, комментарий | да |
| Файлы | фото, акт, протокол | по необходимости |

Свободный ввод там, где существует однозначный справочник, **запрещён**.

## Д10. Справочники и зависимые поля

- Цепочка выбора: организация → здание → этаж → помещение → система → оборудование. Каждый выбор ограничивает следующий.
- Тип оборудования ограничивает набор характеристик. Для огнетушителя: тип, марка, огнетушащее вещество, вместимость; часть параметров подставляется из выбранной модели.
- Единые справочники обязательны, чтобы «ОП-5», «ОП 5» и «оп5» не стали тремя разными сущностями. Нормализация значений выполняется при вводе и при импорте.
- Все справочники расширяются администратором без правки кода.

## Д11. Автоматический контроль сроков и статусы

После выполнения мероприятия следующая дата рассчитывается по назначенному регламенту. Показываются и плановая, и фактическая дата, и число дней до срока или просрочки.

| Статус | Цвет |
|---|---|
| Выполнено | зелёный |
| Предстоит | зелёный |
| Скоро | жёлтый |
| Просрочено | красный |
| Неисправно | красный |
| На ремонте | синий |
| Не эксплуатируется | серый |

Порог «скоро» настраивается пользователем. Отсутствие записи не приравнивается к неисправности — это отдельное состояние «нет данных» (см. документ 00, П2).

## Д12. Массовые операции

- Массовое создание однотипных карточек по шаблону.
- «Создать аналогичные» для группы одинаковых средств.
- Массовая проверка группы однотипных исправных средств — с обязательной фиксацией факта, даты и пользователя.
- Массовое изменение только разрешённых полей, с записью каждого изменения в журнал действий.
- Массовое закрытие типовых мероприятий — только по явному подтверждению.

## Д13. Импорт существующих журналов — обязательная функция

Цель импорта — не загрузить строки, а **превратить старую структуру в нормализованные карточки** объектов, зданий, помещений, систем, оборудования и исторических событий.

Требования:

1. Принимаются XLSX, XLS, CSV и структурированные таблицы; выбирается **один файл или папка с несколькими файлами**. Для Word и прочих неструктурированных документов — распознавание таблиц там, где это технически возможно.
2. Программа анализирует листы, заголовки, типы данных, повторяющиеся значения и структуру таблиц.
3. Сопоставление полей показывается пользователю в виде «старое поле → новое поле → **уровень уверенности**». Высокая уверенность предлагается к автоматическому принятию, сомнительная требует подтверждения.
4. Сопоставление работает по **словарю синонимов и нормализации**, а не по точному совпадению: «№ ОТ» = «№ огнетушителя» = «инв. № ОТ», «ОТВ» = «огнетушащее вещество», «ёмкость» = «вместимость».
5. **Импортёр не угадывает молча.** Любое преобразование, способное изменить смысл данных, показывается до сохранения.
6. Предпросмотр результата: сколько будет создано объектов, оборудования, записей.
7. Неизвестные столбцы не выбрасываются: предлагается сохранить их как дополнительные пользовательские поля или перенести в примечание.
8. Дубликаты выявляются по инвентарному номеру, заводскому номеру, сочетанию «объект + место + оборудование» и другим признакам.
9. Существующие записи не перезаписываются молча: при конфликте пользователь выбирает — объединить, заменить, пропустить, создать новую запись.
10. После импорта карточки объектов, зданий, помещений, систем и оборудования формируются автоматически там, где данных достаточно.
11. Ведётся **журнал импорта**: файл, дата, пользователь, сколько записей импортировано, пропущено, конфликтовало.

## Д14. Фото и документы

- Фото дефекта загружается файлом; съёмка прямо из мобильной версии — после появления серверного варианта (см. Д17).
- Фото автоматически привязывается и к оборудованию, и к конкретному событию проверки.
- Акты, протоколы, паспорта привязываются к объекту, системе, оборудованию или событию.
- Если номер документа извлечён из файла и подтверждён пользователем, повторно его вводить не требуется.

## Д15. Требования к работе пользователя

- Клавиатурный ввод минимален; преобладают выпадающие списки, переключатели, отметки и подставляемые значения.
- Показываются только поля, относящиеся к выбранной системе и виду работ.
- Технические поля базы данных пользователю не показываются.
- Предстоящие и просроченные мероприятия выведены отдельным списком.
- Нажатие на просрочку открывает конкретное оборудование и сразу предлагает провести проверку или создать ремонт.
- После сохранения проверки общий журнал заполнять повторно не нужно.
- Все автоматические изменения обратимы и попадают в журнал действий.

## Д16. Что прямо запрещено

1. Заставлять пользователя вручную переносить существующие журналы Excel.
2. Делать одну универсальную форму на все системы.
3. Требовать повторного ввода объекта, здания, этажа и характеристик оборудования при каждой проверке.
4. Заставлять считать следующие даты вручную.
5. Разрешать свободный ввод там, где есть однозначный справочник.
6. Дублировать одни и те же сведения в общем журнале и в специализированной вкладке ручным вводом.
7. Принимать неоднозначный импорт без подтверждения.

## Д17. Что из дополнения отложено и почему

| Требование | Решение |
|---|---|
| Съёмка фото из мобильной версии | Мобильного клиента в объёме настольного релиза нет. Фото загружается файлом; мобильная съёмка — после серверного варианта (документ 00, раздел 4) |
| Распознавание таблиц в Word и неструктурированных документах | После импорта Excel и CSV, отдельным шагом: качество здесь непредсказуемо, и ставить на него ключевую функцию миграции нельзя |
| Автоматическое извлечение номера документа из файла | После журнала документов; до тех пор номер вводится один раз руками |

## Д18. Порядок реализации дополнения

Требование Д6 (единица отображения — оборудование, колонки — применимые мероприятия) меняет порядок первых шагов относительно прежней редакции: чтобы нарисовать колонку мероприятия, нужно заранее знать, какие мероприятия применимы к типу оборудования. Это минимальные сведения из пакета правил, и без них таблица журнала не строится в принципе — поэтому пакет правил появляется на шаге 1, а не после таблицы.

| Шаг | Содержание |
|---|---|
| 1 | Минимальный пакет правил: перечень применимых мероприятий по типу оборудования (без полного расчёта дат) — по нему определяется набор колонок |
| 2 | Таблица журнала по объектам, уже стоящим на плане: строка — оборудование, колонки — применимые мероприятия, вкладки по типам, фильтры, переходы «показать на плане» и «показать в журнале» |

| 5 | Регламенты и расчёт сроков: периодичность, статусы, цвета, настраиваемый порог «скоро», список предстоящего и просроченного |
| 6 | Чек-листы в пакете правил и сценарий проведения проверки — открывается щелчком по ячейке мероприятия (Д6) |
| 7 | Ремонт и дефекты, связанные с проверкой |

# Дополнение 2. Устройство экрана и режимы работы

Дата: 18.08.2026
Основание: презентация заказчика «Вид ИЖ СППЗ» с макетом экрана и пояснениями к каждой его части

Это дополнение задаёт **облик программы**: из каких полей состоит экран, какие есть режимы и что показывается в каждом. Прежние части ТЗ о структуре объекта, помещениях, журнале и мероприятиях остаются в силе — здесь описано, как всё это собирается в один экран.

Оформление — тёмная тема по макету. Переключатель светлой и тёмной темы остаётся в шапке: макет содержит его значком, а разметка уже построена на переменных цвета.

## П1. Четыре поля экрана

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ШАПКА: логотип │ режимы План/Журнал/Дашборд │ действия │ тема, уведомления│
├───────────────┬──────────────────────────────────┬───────────────────────┤
│ СТРУКТУРА     │  РАБОЧАЯ ОБЛАСТЬ                 │  ДОБАВЛЕНИЕ ЭЛЕМЕНТОВ │
│ ОБЪЕКТА       │  (план / журнал / дашборд —      │  или                  │
│ (дерево)      │   по выбранному режиму и узлу)   │  КАРТОЧКА ЭЛЕМЕНТА    │
│               │                                  │                       │
│ СВЕДЕНИЯ ОБ   │  строка ожидания размещения      │  СОСТОЯНИЕ ЭЛЕМЕНТА   │
│ ОБЪЕКТЕ       │                                  │  (круговая диаграмма) │
└───────────────┴──────────────────────────────────┴───────────────────────┘
```

## П2. Режимы и уровни дерева

Три режима переключаются в шапке. Что показывается — зависит от **уровня выбранного узла**:

| Уровень | План | Журнал | Дашборд |
|---|---|---|---|
| **Организация** | нет | сводный | по всей организации |
| **Цех** | нет | сводный по цеху | **только дашборд** — цех объединяет здания, своего плана у него нет |
| **Здание** | генплан на местности | общий по всем этажам и складам | по всему зданию |
| **Этаж (отметка)** | поэтажный план | только СППЗ этажа | по этому этажу |
| **Склад (резерв СППЗ)** | окно склада: значки хранения запасных средств | журнал склада | по складу |

Переключение режима не сбрасывает выбранный узел, и наоборот: пользователь ходит по дереву, оставаясь в том режиме, в котором работает.

## П3. Режим «План»

### П3.1. Индикация состояния прямо на значке

У каждого значка на плане видно состояние — ободком и точкой, **не занимая много места**: план и так плотный. Четыре состояния те же, что в журнале: в норме, требует внимания, просрочен/неисправен, нет данных.

### П3.2. Закрепление объектов

Кнопка **«Закрепить объекты»** запрещает перетаскивание значков по плану. Расставленное оборудование не должно сдвигаться от случайного движения мышью. Обратная кнопка — «Открепить».

### П3.3. Проверка достаточности первичных средств пожаротушения

Кнопка **«Проверить достаточность и расстановку ПСПТ»** — только для уровня «Этаж».

При нажатии: прочие системы скрываются, остаются огнетушители; от каждого с учётом масштаба плана очерчивается **круг покрытия с полупрозрачной заливкой**; видно, какая часть помещений не покрыта. Радиусы берутся из требований НПА и зависят от объекта — как и все нормативные сведения, они живут в пакете правил, а не в коде.

### П3.4. Строка ожидания

Внизу плана — строка значков, которым ещё не назначено место: перенесённых из правой панели, созданных до загрузки подложки, пришедших импортом. Описана в части 7.3.

### П3.5. Загрузка подложки перетаскиванием

На пустой план можно перетащить файл подложки, на вкладку журнала — существующий журнал предприятия. Описано в частях 5.4 и 9.

## П4. Режим «Журнал»

### П4.1. Вкладки, сгруппированные по цвету

Вкладки видов СППЗ собраны в три цветных блока — чтобы взгляд находил нужную вкладку сразу, а не читал два десятка названий подряд:

| Блок | Что входит |
|---|---|
| **Снаружи здания** | гидранты, водоёмы, наружные лестницы, ограждения кровли, места подключения техники, проезды |
| **Внутри здания** | огнетушители, краны ВПВ, щиты, выходы, двери, знаки — всё, кроме пожарной автоматики |
| **Системы пожарной автоматики** | извещатели, приборы, оповещатели СОУЭ, АУПТ, противодымная защита, задвижки |

### П4.2. Строка — один элемент

Строка журнала — одна единица оборудования; в остальных графах — все записи о проверках и работах. У каждого вида систем свой набор обязательных записей. Рядом с наименованием — цветовой индикатор состояния. Закреплено в части Д6 Дополнения 1.

### П4.3. Выгрузка и печать

Кнопки **«Выгрузить в Excel»**, **«Выгрузить в Word»**, **«Выгрузить в PDF»**, **«Печать»**. Выгружается то, что видно с учётом вкладки и фильтров: пользователь печатает именно тот журнал, который просматривает.

## П5. Режим «Дашборд»

Показатели по выбранному узлу и всему, что в него входит.

- **Плитки**: всего элементов, в норме, требует внимания, просрочено/неисправно, нет данных — с долями в процентах.
- **Состояние по системам** — разбивка на снаружи / внутри / автоматика.
- **Просроченные проверки** — списком: элемент, дата, место.
- **Работы на ближайшие 7 дней** — что предстоит и в каком количестве.
- **Документы и заявки** — открытые и просроченные заявки.

## П6. Правая панель: два режима

### П6.1. Добавление элементов

Значки видов СППЗ, наглядно отражающие суть элемента. Перетаскивание на план создаёт объект и строку журнала одновременно; перетаскивание в журнал создаёт строку, а значок встаёт в строку ожидания.

**При работе с карточкой элемента эта часть сворачивается** — панель одна, режима два (закреплено в части 6.5).

### П6.2. Карточка элемента

- значок, наименование, **видимая индикация состояния**;
- характеристики — свои для каждого вида элемента, по составу записей журнала;
- **«Состояние элемента»** — круговая диаграмма по всем элементам узла: сколько в норме, требует внимания, просрочено, нет данных;
- **групповая карточка**: при выделении нескольких элементов показывается вид, количество и общая диаграмма состояний.

### П6.3. Три кнопки: История, Чек-лист проверки, Заявка

Открываются **окном поверх двух левых полей** — чтобы работать с элементом, не теряя из виду план и дерево.

| Кнопка | Что показывает |
|---|---|
| **История** | что и когда происходило с элементом, кто вносил записи, архив документов — строками, как в журнале, но подробнее и удобнее для чтения |
| **Чек-лист проверки** | экран проверки, при необходимости разделённый на несколько окон — по одному на каждый предусмотренный вид проверки. Пункты отмечаются галочками (выполненный зачёркивается), можно приложить фотографии, документы и комментарии. Результат уходит в историю, в журнал и меняет состояние элемента. **Групповая отметка**: можно выбрать сразу несколько схожих элементов и закрыть их одним чек-листом |
| **Заявка** | формирование заявки на обслуживание по видам элементов: выбор нескольких элементов и заявка в стороннюю организацию |

## П7. Левое поле

### П7.1. Структура объекта

Дерево, где одно вложено в другое. Пользователь создаёт узлы сам и называет как ему нужно; вид (уровень) узла предлагается **выпадающим списком**. Выбранный узел подсвечивается, и от него зависит всё правее.

Для подразделения и здания могут назначаться **права доступа** — заготовка на будущее, вместе с учётными записями.

### П7.2. Сведения об объекте

Карточка выбранного узла: значимые для пожарной безопасности сведения. Для здания — класс функциональной пожарной опасности, степень огнестойкости и прочее выбором из списка (часть 4). На уровне этажа — **помещения с категорией по взрывопожарной опасности и возможностью отметить помещение на плане** (часть 5.5).

## П8. Фильтры

| Режим | Что фильтруется |

| **План** | по видам показываемых систем — галочками рядом со значком, причём показаны только виды, присущие выбранному узлу; и по состоянию элементов |

## П11. Окно склада

У склада нет плана: где именно на полке лежит запасной огнетушитель, никому не
нужно — важен состав. Поэтому в режиме рабочей области склад показывает
**перечень оборудования, сгруппированный по видам**: заголовок вида со знаком и
количеством, под ним учётные номера. Ободок каждого номера окрашен по состоянию
так же, как значок на плане, — язык цвета один на всю программу.

Щелчок по номеру открывает карточку в правом поле. Элемент, брошенный в окно
склада из правой панели, заводится без места установки и сразу попадает в журнал
склада — та же строгая связь журнала и графической части, что и на плане.

Сюда же заводится оборудование, числящееся за пожарной техникой: склад с
названием машины. Это исключение из правил структуры, а не отдельный вид узла.

## П12. Сверка с макетом «Вид ИЖ СППЗ» — что исправлено

Заказчик прислал презентацию с точным описанием кнопок и логики и визуальный
макет (тёмная тема, три режима на одном экране). Первый проход по Дополнению 2
разошёлся с этим макетом в нескольких местах. Разошедшееся исправлено:

- **Подсчёт на дашборде вёлся по мероприятиям, а не по элементам.** У одного
  огнетушителя три мероприятия, поэтому «Всего элементов: 271» и разбивка по
  статусам не складывались друг в друга — читателю предлагались проценты,
  которые ни с чем не сходятся. Заказчик считает иначе: один элемент — один
  статус, худший из его мероприятий. Так и переписано (`worstObjectStatus` в
  ядре, `packages/core/src/rules/activity-status.ts`) — теперь пять чисел на
  дашборде всегда складываются в общее число элементов, как в макете. Эта же
  функция заменила четыре чуть разных копии одной и той же логики в
  `PlanCanvas`, `ObjectCard`, `JournalPanel` и `StoragePanel` — расхождение
  между ними было вопросом времени, а не «если».
- **Кольцевых диаграмм не было вовсе** — только числа и списки с точками.
  В макете круг встречает читателя первым, до всякого списка. Добавлен
  переиспользуемый `DonutChart` (SVG, без библиотек) — на дашборде для общего
  состояния и для состава по трём системам.
- **Индикация состояния на значке плана рисовалась цветной обводкой всего
  значка** — в ТЗ уже было предупреждение «не должна занимать много места»,
  но реализация ему не следовала. Заменено на маленькую точку в углу значка,
  как в макете: заливка значка по-прежнему говорит, какой это тип
  оборудования, а точка — в каком он состоянии.
- **Журнал показывал только следующую дату мероприятия**, без даты последнего
  выполнения, и без фильтра по помещению или текстового поиска — в макете у
  каждого мероприятия две колонки, «Последняя» и «Следующая», плюс фильтры по
  помещению и поиск по журналу. Таблица переписана под эту структуру
  (двухстрочная шапка с `colSpan`), добавлена колонка общего статуса строки.
  Для этого понадобилось новое чтение: `RoomRepository.list()` — раньше
  помещения читались только по одному этажу, а журнал здания должен показывать
  настоящие названия помещений с чужих этажей, а не только название этажа.
- **Цвета трёх блоков журнала** (снаружи/внутри/автоматика) не совпадали с
  макетом — подобраны заново: синий/зелёный/красный.
- **Заголовки правой панели** не совпадали с формулировками заказчика:
  «Библиотека элементов» → «Добавление элементов»; при выбранном объекте
  теперь заголовок — название и учётный номер элемента с пилюлей состояния
  рядом, как в макете, а не отдельная неизменная надпись «Карточка объекта».

Сознательно не тронуто в этом проходе — расхождение с макетом отмечено, но
это отдельная работа, не косметика:

- **масштаб и панорама плана** (значки +/−, вписать по размеру, подпись
  масштаба «1:100») — в макете это часть экрана «План», у нас плана размер
  задаётся растяжением по ширине без масштабирования;
- **временной период на дашборде** («Период: весь период») — фильтра по
  датам на дашборде нет;
- **круговая диаграмма состояния группы объектов** при множественном выборе
  на плане или в журнале — это шаг 14 (групповая карточка), в один проход с
  текущим не поместился;
- **значки-пиктограммы вместо двухбуквенных кодов** в библиотеке и на плане —
  у заказчика в макете иконка похожа на реальный предмет (огнетушитель,
  лестница), у нас — цветной кружок с кодом системы; смена требует набора
  SVG-иконок, а не логики.

## К1. Формат дат в интерфейсе

Все даты, которые видит или вводит пользователь, — российский формат
**ДД.ММ.ГГГГ** (пример: 18.08.2026). Требование распространяется на все
экраны, журналы, карточки объектов, фильтры, отчёты, печатные формы,
экспортируемые документы и уведомления. Формат ММ/ДД/ГГГГ и другие
представления в интерфейсе не использовать.

Это требование к **показу**, не к хранению. Правило AGENTS.md — календарная
дата хранится и передаётся между слоями программы как строка `ГГГГ-ММ-ДД`,
без часового пояса — не отменяется и не может быть отменено: оно защищает от
сдвига даты при смене часового пояса компьютера. Меняется только то, что
показывается человеку и что он вводит: между хранением (ISO) и показом
(ДД.ММ.ГГГГ) нужен один форматтер на всё приложение, а не форматирование в
каждом компоненте по отдельности.

**Меняет:** сейчас даты в журнале, истории объекта, карточке, списках
дашборда и мастере импорта показываются как есть, то есть в формате
`ГГГГ-ММ-ДД` (например, ячейки статуса в `JournalPanel`, даты в
`ObjectHistoryModal`, просроченные проверки в `DashboardPanel`). Нужно завести
`formatDateRu(iso: IsoDate): string` рядом с `today.ts` и пройти по всем местам
вывода дат. Поля ввода `<input type="date">` можно не переделывать: браузер
показывает их по локали ОС, а хранит по-прежнему ISO в атрибуте `value` — это
уже соответствует требованию без переделки.

## К2. Компактные вкладки журнала

Вкладки видов оборудования внутри цветных блоков журнала (часть П4.1) не
должны содержать длинные полные названия — это делает вкладки неудобно
широкими. Основной способ — пиктограмма вида оборудования, при необходимости
рядом короткое сокращение. Полное название — во всплывающей подсказке при
наведении.

Это тот же самый пробел, что отмечен в части П12 как сознательно отложенный
(«значки-пиктограммы вместо кодов»), но теперь это прямое требование, а не
расхождение с макетом на будущее. Набор пиктограмм нужен один на всё
приложение: он используется и здесь, и в библиотеке элементов (часть 6), и на
значках плана (часть П3.1) — заводить его для одного места означает
переделывать работу трижды.

## К3. Нижняя панель фильтрации — заменяет верхние выпадающие списки

**Меняет часть П8 и уже реализованные фильтры (часть П12):** сейчас фильтры
плана и журнала — выпадающие списки с одиночным выбором в верхней панели
инструментов (`.plan-filters`, `.journal-toolbar`). Требование заказчика —
перенести управление отображением в **нижнюю панель** рабочей области,
чекбоксами с множественным выбором, без выпадающих списков.

- **Состояние** — пять чекбоксов: В норме, Требует внимания, Просрочено,
  Неисправно, Нет данных. Можно отметить несколько сразу. Отметка применяется
  сразу, без подтверждения.

  Отметим неточность в тексте заказчика для проверки при постановке: сейчас
  «Просрочено» и «Неисправно» в программе — разные оси (регламентный статус
  мероприятия и техническое состояние оборудования, часть Д9), а не два
  значения одного списка «Состояние». Нужно уточнить у заказчика: либо это
  два независимых чекбокса из разных наборов, показанных в одной панели,
  либо требование сознательно объединяет обе оси в один фильтр — тогда фильтр
  должен опрашивать оба поля объекта.

- **Вид системы** — отдельный чекбокс на каждый вид оборудования, тоже
  множественный выбор.
- Обе группы фильтров работают одновременно, по «И»: например, «Требует
  внимания» + определённые виды систем показывает только их пересечение.
- Один и тот же принцип и разметка — на плане и в журнале. На плане фильтр
  решает, какие значки показаны; в журнале — какие строки показаны.
- Панель должна быть узкой по высоте и не мешать основной таблице или плану:
  постоянная или легко разворачиваемая полоса снизу, а не отдельный экран.

## К4. Интерактивный дашборд — переход от показателя к списку

**Меняет часть П5 и текущую реализацию `DashboardPanel`:** сейчас кликабелен
только список просроченных проверок (переход к карточке объекта). Все
остальные плитки и разделы — только для чтения.

Требование: **каждая** плитка и карточка дашборда кликабельна и ведёт к
списку элементов с уже применённым фильтром того же смысла, что показатель.
Нажатие на «В норме» открывает журнал/план, отфильтрованный по состоянию
«норма» (тот же фильтр, что в части К3, только выставленный программой, а не
руками); нажатие на плитку вида системы — тот же журнал, отфильтрованный по
этому виду. Принцип: **показатель → отфильтрованный список → карточка
конкретного объекта** — тот же путь, что уже есть у просроченных проверок,
нужно провести его через весь дашборд.

Дашборд должен также стать содержательнее: помимо уже показанных чисел —
компактный набор ключевых показателей по состояниям, по видам систем,
просроченным проверкам, требующим внимания, неисправным и записям без данных
(многое из этого уже есть после части П12, донат по системам и по статусам
уже строится — здесь усиление, а не работа с нуля).

Пиктограммы к показателям дашборда — тот же набор, что в К2, для
единообразия.

## К5. Состояние «Закрепить объекты» — хранится по плану, не по сессии

**Меняет часть П3.2 и текущую реализацию:** сейчас `pinned` — состояние
React-компонента `MainScreen`, которое явно сбрасывается при смене
выбранного узла (`useEffect(() => setPinned(false), [selectedId])`) и
пропадает при закрытии программы.

Требование: закрепление — свойство **конкретного плана** (узла дерева), а не
текущего сеанса работы. Если пользователь закрепил объекты на плане этажа,
это состояние остаётся при переходе на другой этаж и обратно, при переходе в
журнал и обратно, и должно быть таким же после перезапуска программы. Меняет
это состояние только явное нажатие «Раскрепить» на этом же плане.

Практически: `pinned` переходит из состояния компонента в поле узла дерева
(например, `TreeNode.objectsPinned: boolean`, по аналогии с
`inCommonJournal`) и сохраняется через `ObjectTreeRepository.save`, а не
`useState`. Нужна миграция уже существующих узлов на чтение (отсутствующее
поле = `false`, объекты не закреплены — как сейчас по умолчанию).

## К6. Карточка объекта — иерархические справочники вместо свободного текста

**Расширяет часть 6 и Д10:** типовые характеристики оборудования должны
выбираться из зависимых выпадающих списков, а не вводиться текстом — это
устраняет ошибки ввода и делает фильтрацию и контроль сроков надёжными.

### К6.1–К6.4. Огнетушители: тип → модель

Два зависимых списка вместо одного текстового поля «Марка, модель»:

1. **Тип огнетушителя** — верхний уровень справочника: порошковый (ОП),
   углекислотный (ОУ), воздушно-пенный и другие типы по действующему
   справочнику; отдельно — переносной/передвижной (перевозной) как
   исполнение; **BONTEL — воздушно-эмульсионный тип внутри общей строки
   «Огнетушитель»**, а не отдельный элемент библиотеки.
2. **Модель/типоразмер** — второй список, состав которого зависит от
   выбранного типа (например, тип «порошковый» → ОП-2, ОП-5 и другие
   типоразмеры этого типа).

Справочник — расширяемый набор данных (в духе `RULE_PACKAGE` и
`ELEMENT_CATALOG`: данные, не код), а не жёстко ограниченный список — новые
типы и модели должны добавляться без изменения программы.

**BONTEL — отдельная логика контроля.** У этого типа свои правила
периодичности проверок, ТО и перезарядки, отличные от обычных огнетушителей.
При выборе BONTEL карточка должна применять именно этот набор полей и правил
— так же, как уже разделены `extinguisher-water/powder/co2` по разным
периодичностям перезарядки (часть П12 упоминает этот принцип, здесь он
явно распространяется на BONTEL как подтип огнетушителя).

**Автоматическое формирование карточки.** После выбора типа и модели
программа сама подставляет применимые характеристики, периодичность контроля
и способ проверки массы (для моделей, где он предусмотрен), и показывает
только относящиеся к этому типу поля. Пользователь не заполняет то, что
однозначно следует из типа и модели. Это тот же принцип «однократный ввод —
многократное использование», уже зафиксированный в части Д1, применённый к
самой карточке оборудования, а не только к датам мероприятий.

### К6.5. Общий принцип — для всех видов оборудования

Тот же каскад (вид → тип → модель/исполнение) — общий принцип построения
карточек по всей программе, не частная особенность огнетушителей. При
добавлении карточек для других систем (краны, извещатели, оповещатели и
так далее) заводить их по этому же образцу.

Администратору должна быть доступна настройка и актуализация справочников —
это связано с частью Д10 (справочники с расширением администратором),
отмеченной как несделанная в Дополнении 1.

## К7. Контекстное меню объекта на плане: «Переместить» и «Заменить»

Новая функция: правая кнопка мыши по значку объекта на плане открывает
контекстное меню с операциями над этим объектом. Сейчас у значка есть только
обычный щелчок (выбор → карточка) и перетаскивание; контекстного меню нет.

### К7.1. «Переместить»

Открывает дерево объекта текущего цеха/объекта (здания, этажи, помещения,
склад). Пользователь выбирает место назначения; после подтверждения объект
переносится туда с сохранением характеристик, истории и идентификатора,
исчезая с прежнего места. Пример из требования: огнетушитель со склада —
через контекстное меню на первый этаж, в выбранное помещение.

Технически это то же перемещение, что уже умеет `moveObject` (часть 7,
`nodeId`/`roomId`/`position` объекта), но с другим способом выбора места:
не перетаскиванием на конкретный план, а выбором узла из дерева — нужно
целиком для объектов на складе (там нет координат, часть П11) и для переноса
между этажами без визуального перетаскивания через несколько экранов.

### К7.2. «Заменить»

Открывает список совместимых типов/моделей из того же иерархического
справочника (часть К6). После подтверждения новый объект встаёт на то же
место на плане; связь со старым объектом фиксируется в истории. Новый объект
живёт по своим характеристикам, типу и нормативным срокам — сроки не
наследуются от заменённого оборудования.

Это **новый объект**, а не правка старого — правило неизменяемости истории
(часть Д1, AGENTS.md) запрещает переписывать характеристики оборудования
задним числом. Связь «заменён на / заменяет» — новое поле или новая запись в
истории, которых сейчас в `PlanObject`/`MaintenanceEvent` нет.

### К7.3–К7.4. История и ограничения

Обе операции фиксируются в истории объекта: дата, время, пользователь;
«Переместить» — прежнее и новое расположение, «Заменить» — прежний и новый
объект. Текущий `MaintenanceEvent` для этого не подходит — он моделирует
мероприятие по чек-листу, а не смену расположения или замену; нужен свой вид
записи истории (или общая лента событий узла/объекта, часть Д4, расширенная
этими двумя видами).

Перемещение и замена учитывают права доступа (часть 3.1, права по
подразделениям и зданиям — сейчас не реализованы), состояние закрепления
(часть К5: закреплённый объект не должен переноситься перетаскиванием, но
вопрос, распространяется ли это ограничение на «Переместить» из меню, нужно
уточнить у заказчика) и структуру дерева — перенос за пределы текущего
объекта/цеха обычным пользователем не допускается.

## К8. Чек-лист проверки — единое окно на несколько видов работ

**Меняет часть Д7–Д8 и текущий `MaintenanceModal`:** сейчас одно мероприятие
(`activityCode`) открывает один чек-лист, и результат (`MaintenanceResult`) и
дефект — один на всё событие. Требование заказчика описывает более гибкий
сценарий одной проверки:

1. Пользователь открывает окно «Чек-лист проверки» и сам отмечает, какие виды
   работ фактически выполнялись за этот визит (например, «Осмотр»,
   «Испытание», «Проверка клапанов», «Перекатка рукава» — набор видов работ
   свой для каждого типа оборудования).
2. Под каждый отмеченный вид работ — своя вкладка или раздел со своим
   чек-листом и своими пунктами.
3. У каждого пункта — не только галочка (пункт зачёркивается при выполнении),
   но и **отдельный результат**: «Выполнено», «Выполнено, есть замечание»,
   «Не выполнено». «Выполнено, есть замечание» — самостоятельное состояние,
   не приравнивается автоматически к полностью исправному результату.
4. При результате «Выполнено, есть замечание» — поле текста замечания у
   этого пункта, визуально выделенное красным.
5. Поля исполнителя и примечания — на весь визит (как сейчас), сохраняются
   вместе с результатами.
6. По завершении — сводка: сколько пунктов выполнено, с замечаниями, не
   выполнено, по всем отмеченным видам работ вместе.
7. Критический дефект может переводить объект в состояние «Неисправно» или
   «Требует внимания» по правилам, настроенным для конкретного вида системы
   — правило заводится как данные (в духе `RULE_PACKAGE`), не как код проверки
   под конкретный тип оборудования.

**Модель данных меняется заметнее интерфейса.** Сегодня `ChecklistAnswer` —
это `{ item: string; ok: boolean }`, а `MaintenanceEvent` привязан к одному
`activityCode` с одним результатом на всё событие. Новому сценарию нужно:

- результат и (опционально) текст дефекта на **каждый пункт**, а не на всё
  событие;
- одна проверка (один визит) может закрывать **несколько видов работ**
  (`activityCode`) сразу — сейчас это означало бы несколько отдельных
  `MaintenanceEvent`; нужно решить, заводить ли одну запись на визит с
  несколькими блоками чек-листа внутри, или как раньше — несколько записей,
  но создаваемых из одного окна за одно сохранение (второе меняет меньше
  существующего кода и сохраняет текущий принцип «одно мероприятие — одна
  запись истории», часть Д5).

Это решение нужно принять явно на следующем шаге, а не по ходу разработки —
от него зависит, как считается статус в `activityCellsForObject` и
`worstObjectStatus` (часть П12), и как это ляжет на уже готовый пакет правил.

### Как решены открытые вопросы при реализации

- **К3**: неточность про «Просрочено»/«Неисправно» решена так — это два
  независимых тега, у объекта может стоять оба сразу, чекбоксы отмечают их
  по отдельности; пустой выбор фильтра по-прежнему значит «показать всё».
  Требует подтверждения заказчика, что это верное прочтение.
- **К6**: справочник моделей заведён для порошковых, углекислотных, водных,
  пенных и воздушно-эмульсионных огнетушителей BONTEL. Для BONTEL официальный
  паспорт изготовителя назначает перезарядку и переосвидетельствование один
  раз в 10 лет. Пожарные извещатели и системы пожаротушения также объединены
  в общие строки библиотеки с выбором подтипа в карточке. Для видов без
  подтверждённого справочника моделей поле остаётся текстовым.
- **К7**: сделаны обе операции — «Переместить» (новый сценарий
  `relocateObject`, ядро) и «Заменить» (переиспользует уже готовые
  `placeObject` + `archiveObject`, отдельного сценария не понадобилось).
  **Запись в историю не сделана** — `MaintenanceEvent` не подходит по смыслу
  (это не мероприятие по чек-листу), а заводить отдельную сущность истории
  перемещений/замен в этом проходе не стали, чтобы не расширять модель данных
  ещё раз при уже большом объёме изменений за один раз. Права доступа тоже не
  проверяются — в программе их пока нет вообще (часть 3.1 отмечена как не
  реализованная).
- **К8**: выбрана вторая из двух схем, названных в черновике — одно
  мероприятие = одна запись `MaintenanceEvent`, несколько отмеченных видов
  работ дают несколько записей за одно сохранение окна. `ChecklistAnswer`
  изменена: вместо `ok: boolean` — `result: ChecklistItemResult` (три
  значения) и `defect: string | null` на каждый пункт. Итоговый результат и
  дефект события считаются от худшего пункта чек-листа автоматически,
  отдельно их не спрашивают.

Порядок реализации выполнен последовательно К1 → К8, каждый шаг проверен
типами и тестами (`npm run check`, 333 теста) перед переходом к следующему.

### К8.7. Совместимость ранее сохранённых чек-листов

При чтении локального хранилища приложение обязано автоматически преобразовать
старый ответ пункта `{ ok: boolean }` в новую модель с полем `result`. Значение
`ok: true` преобразуется в «выполнено», `ok: false` — в «не выполнено».
Существующая история проверок при обновлении программы не удаляется. Для
результата пункта «выполнено с замечанием» или «не выполнено» комментарий
обязателен; это правило проверяется не только интерфейсом, но и ядром программы.

### П4.3.1. Реализованные форматы выгрузки журнала

Выгрузка строится из того же набора строк, который пользователь видит после
выбора вида оборудования, помещения, статусов и строки поиска. В файл входят
идентификатор оборудования, модель, место установки, техническое и регламентное
состояние, а также для каждого применимого мероприятия — последняя дата,
следующая дата и статус.

- **Excel** — настоящий файл XLSX с одной страницей «Журнал СППЗ»; архив XLSX
  формируется собственным модулем без внешних библиотек и проверяется тем же
  движком E7, которым программа импортирует журналы;
- **Word** — табличный документ DOC с русской кодировкой;
- **PDF** — альбомная страница A4, формируемая печатным движком Electron;
- **Печать** — системное окно выбора принтера для того же табличного снимка.

Отмена системного окна сохранения не считается ошибкой и не создаёт пустой файл.

# Дополнение 4. Правки дерева объектов и карточек узлов

Источник уточнения: `ИЖ_СППЗ_правки_дерево_объектов_для_Codex.docx`.
Настоящее дополнение уточняет части 3-4 действующего ТЗ и заменяет прежний
интерфейсный способ ручной перестановки узлов кнопками.

## Л1. Общая логика дерева объектов

В левом поле «Дерево объектов» пользователь меняет порядок узлов мышью:
зажимает левую кнопку на строке узла и переносит его выше или ниже. Такое
перетаскивание является только сортировкой и не меняет родителя.

Сортировка разрешена только внутри текущего родителя:

- этажи переставляются только внутри одного здания;
- склады переставляются только внутри одного здания вместе с соседними
  допустимыми узлами этого же родителя;
- здания переставляются только внутри одного цеха или организации;
- цеха переставляются только внутри своей организации.

Перенос узла к другому родителю выполняется только осознанной командой
контекстного меню «Выбрать нового родителя / Перенести». При переносе ядро
обязательно проверяет допустимость иерархии по типам узлов и не допускает
перенос в другую организацию.

Иерархия остаётся типизированной. При создании дочернего узла интерфейс
показывает только допустимые типы из правил дерева: под зданием нельзя создать
цех; для здания доступны только этажи и склады; под этажом нельзя создать
дочерний узел дерева.

## Л2. Контекстное меню узла дерева

Правая кнопка мыши на строке узла открывает компактное контекстное меню:

- «Удалить» — пользовательский термин для вывода узла из эксплуатации; физическое
  удаление данных запрещено общими правилами проекта;
- «Выбрать нового родителя / Перенести» — открывает выбор допустимого нового
  родителя.

Операции не дублируются лишними кнопками внутри карточки узла. Кнопки «Выше» и
«Ниже» удаляются из карточки полностью, так как сортировка выполняется
drag-and-drop. Кнопка/переключатель «Показать выведенные из эксплуатации
объекты» удаляется из основного интерфейса дерева.

Контекстное меню закрывается при выборе команды, при нажатии Escape и при
щелчке мышью в любое место вне меню. Меню не должно оставаться поверх
интерфейса после перехода пользователя к другой области экрана.

## Л3. Состав карточек узлов

### Л3.1. Организация

В карточке организации остаются:

- «Наименование»;
- «Вид организации».

Поле «Код» и кнопки сортировки «Выше»/«Ниже» в карточке организации не
показываются.

### Л3.2. Цех

В карточке цеха остаются:

- «Название»;
- «Код».

Не показываются: «Рабочая область», признак «нет узла, только группирует»,
«Состояние», кнопки «Выше»/«Ниже». Ограничение допустимых дочерних типов
сохраняется через правила дерева.

### Л3.3. Здание

В карточке здания остаются:

- наименование/вид узла;
- название;
- инвентарный номер;
- класс функциональной пожарной опасности;
- степень огнестойкости;
- класс конструктивной пожарной опасности;
- этажность;
- количество подземных этажей;
- высота здания;
- площадь застройки;
- строительный объём;
- категория здания по взрывопожарной опасности;
- документ-основание определения категории;
- количество эвакуационных выходов;
- год постройки;
- ответственный за пожарную безопасность;
- остальные существующие поля, не указанные к удалению.

Добавляются поля:

- «Чердак»;
- «Мансардный этаж».

Порядок блока этажности в карточке здания: «Этажность», затем «Чердак», затем
«Мансардный этаж», затем «Количество подземных этажей», после этого высота,
площади и остальные характеристики.

Из карточки здания убираются: «Рабочая область», «Состояние: в работе», типы
систем оповещения, пожарная сигнализация, пожарная автоматика, внутренний
противопожарный водопровод, противодымная защита, типы лестничных клеток,
перечень/типизация эвакуационных выходов, кнопки «Выше»/«Ниже». Поле
«Количество эвакуационных выходов» остаётся.

### Л3.4. Этаж

В карточке этажа остаются:

- «Наименование»;
- «Вид»;
- «Название» с понятной подсказкой, например «Первый этаж» или «Отметка ...»;
- раздел работы с помещениями;
- категории помещений.

В списке помещений кнопка обводки называется «Отметить на плане», а команда
вывода помещения из действующего списка называется «Удалить» (фактически это
архивация без физического удаления записи).

Не показываются: «Рабочая область», «Состояние», «Код или номер», отдельное
поле «Отметка», кнопки «Выше»/«Ниже». Перенос этажа к другому допустимому
родителю остаётся только через контекстное меню «Выбрать нового родителя /
Перенести».

## Л4. Критерии готовности

- пользователь меняет порядок зданий внутри одного цеха и этажей внутри одного
  здания простым перетаскиванием мышью;
- drag-and-drop сортировки не позволяет случайно перенести здание в другой цех
  или этаж в другое здание;
- смена родителя возможна только через контекстное меню и только при валидной
  иерархии;
- в интерфейсе отсутствуют кнопки «Выше», «Ниже» и «Показать выведенные из
  эксплуатации объекты»;
- карточки организации, цеха, здания и этажа приведены к составу полей из
  раздела Л3;
- при создании узлов интерфейс не предлагает недопустимые типы дочерних
  объектов.

# Дополнение 5. История пользовательских команд Undo/Redo

В шапке программы должны быть кнопки «Назад» и «Вперёд». «Назад» отменяет
последнюю пользовательскую команду, «Вперёд» возвращает отменённую команду.
Глубина истории — не менее 10 команд.

История строится не как снимок локальных JSON-файлов, а как журнал команд и
изменений сущностей:

- пользовательское действие открывает команду (`begin`);
- все сохранения сущностей внутри действия попадают в эту команду;
- успешное действие закрывается (`commit`) и становится одним шагом Undo;
- при ошибке команда отменяется (`cancel`);
- Undo применяет значения `before` в обратном порядке;
- Redo применяет значения `after` в исходном порядке.

Одна команда может включать несколько записей. Например, сортировка дерева
меняет порядок нескольких узлов, групповое создание создаёт несколько объектов,
а единый чек-лист проверки создаёт несколько мероприятий. Для пользователя это
остаётся одним действием и откатывается одним нажатием.

История Undo/Redo — это техническая история правок интерфейса, а не журнал
эксплуатации СПЗ. В коммерческой серверной версии к команде должны добавиться
пользователь, права доступа, рабочая сессия и аудит, но принцип останется тем
же: отменяется команда, а не произвольный снимок файлового состояния.

На текущем локальном этапе команда хранит изменения сущностей дерева, помещений,
объектов СПЗ, мероприятий, настроек и подложек через отдельный адаптер хранения.
При переходе на SQLite или сервер меняется адаптер применения истории, а не
сценарии ядра и не интерфейсные команды.

# Дополнение 6. Загрузка и подготовка подложек планов

Подложка используется на двух уровнях дерева:

- здание — «Генплан объекта»;
- этаж/отметка — «Поэтажный план».

После загрузки подложки поверх неё должна отображаться подпись выбранного узла
дерева, например «Организация / Цех / Здание / 1 этаж». Подпись выводится как
интерфейсная плашка поверх плана и не изменяет само изображение.

## М1. Поддерживаемые источники

Программа должна принимать наиболее ходовые форматы планов и приводить их к
единому рабочему виду:

- PDF;
- PNG;
- JPEG/JPG;
- SVG;
- DXF;
- JSON-описание подложки;
- DWG — через экспорт/конвертацию в DXF, SVG или PDF либо через отдельный
  лицензированный коммерчески допустимый модуль.

Исходный файл сохраняется без изменений. Рабочая подложка создаётся отдельно и
приводится к единому растровому формату PNG. Это нужно, чтобы разные этажи
выглядели одинаково и чтобы дальнейшие операции очистки, масштабирования,
нанесения СППЗ и печати работали одинаково независимо от исходного формата.

Формат файла определяется по содержимому, а не только по расширению.

## М2. Лицензионная и архитектурная граница

В базовую поставку нельзя добавлять интернет-зависимые сервисы, неразрешённые
библиотеки или компоненты с неясными правами коммерческого использования.

Для DWG не допускается имитация полноценной поддержки закрытого формата без
правовой проверки. Базовый безопасный путь: пользователь экспортирует DWG в
DXF/SVG/PDF, либо в будущей коммерческой версии подключается отдельный
лицензированный конвертер как сменный движок. Остальная программа не должна
зависеть от конкретного конвертера.

## М3. Очистка подложки

После загрузки пользователь попадает в подготовку подложки. Подготовка должна
позволять:

- работать как лаконичный процесс из трёх шагов: сначала вырезать нужный
  фрагмент, затем автоматически подготовить архитектурную основу, затем при
  необходимости выполнить ручную доочистку;
- вырезание рабочей области является первым этапом, а не отложенной операцией:
  после выбора области экран подготовки должен показывать уже только этот
  фрагмент, и все следующие действия должны выполняться в координатах нового
  рабочего листа;
- убрать цветные элементы: зелёные пути эвакуации, красные значки, цветные
  зоны и их сглаженную кайму;
- после удаления цветного приводить рабочую основу к монохромному виду:
  фон — белый, архитектурные линии — чёрные, без цветных остатков и «грязи»
  от сглаживания;
- не менять планировку при удалении цветного: если цветная линия наложена на
  стену или пересекает её, после удаления не должен оставаться разрыв стены.
  Для растровых изображений, где исходная стена под цветом уже потеряна,
  допускается восстановление короткого разрыва только по продолжающейся
  длинной тёмной линии с двух сторон. Малые чёрные рамки значков и пиктограмм
  не должны автоматически восстанавливаться как стены;
- убрать текстовые подписи и мелкие служебные обозначения без OCR, по
  графическим признакам мелких связных компонентов;
- убрать отдельный цвет по палитре подложки;
- убрать лишний значок, стрелку или подпись щелчком по фигуре;
- вырезать нужную область чертежа, чтобы лишние поля и рамки не попадали в
  рабочую подложку;
- после выбора рабочей области удалять ненужные прямоугольные области внутри
  неё: легенду, экспликацию, штамп, боковые и верхние надписи; удалённая область
  становится белым фоном;
- оставить только тёмные линии, если исходник является сканом с серостью,
  заливками или шумом.

Очистка должна быть неразрушающей: хранится исходник и список операций очистки.
Пользователь может отменить очистку и применить её заново с другими настройками.
Результат очистки должен иметь версию алгоритма; если алгоритм изменился,
старый сохранённый PNG не должен молча считаться актуальной подложкой.

## М4. Качество преобразования

При преобразовании нужно максимально сохранять читаемость контура здания:

- толстые линии должны оставаться толстыми;
- тонкие линии должны оставаться тонкими;
- стены, проёмы, лестницы и основные контуры не должны удаляться при очистке
  цветных элементов и подписей;
- цветные элементы и текст должны удаляться как вспомогательные данные, если
  пользователь включил соответствующие операции;
- по всем этажам одного здания рабочие подложки должны приводиться к визуально
  сопоставимому виду.

Если автоматическая очистка не дала идеальный результат, пользователь должен
иметь ручные инструменты доочистки: удалить ненужную область, убрать фигуру
щелчком, убрать отдельный цвет, вырезать нужную область.

Масштаб задаётся после подготовки и очистки подложки, чтобы пользователь
калибровал уже тот рабочий лист, который будет использоваться в плане.
