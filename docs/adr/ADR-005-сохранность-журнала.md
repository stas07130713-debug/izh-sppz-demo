# ADR-005. Сохранность журнала эксплуатации

Дата: 19.08.2026
Состояние: принято, реализовано

## Обстоятельства

Разбор кода перед продолжением разработки вскрыл три дефекта, каждый из которых
приводил к безвозвратной потере журнала эксплуатации. Журнал предъявляется при
проверке МЧС, восстановить его неоткуда, поэтому решения ниже приняты как
обязательные, а не как улучшения.

### 1. Обрыв записи уничтожал историю

Все хранилища писали `writeFile` прямо поверх рабочего файла, а чтение
перехватывало любую ошибку и возвращало пустой список:

```ts
} catch {
  // Файла ещё нет — обычное состояние
  return [];
}
```

Комментарий предполагал только отсутствие файла, но `catch` ловил и ошибку
разбора. Цепочка воспроизведена:

```
1. Журнал в порядке:               записей = 60
2. Обрыв записи (нет temp+rename): файл повреждён
3. Чтение повреждённого файла:     записей = 0   <- молча, без ошибки
4. Одна новая запись затирает всё: записей = 1
```

### 2. Отмена действия стирала записи журнала

Появившийся Undo/Redo регистрировал журнал наравне с прочими сущностями:
`collectionAdapter('maintenance', maintenanceFile, 'events')`. Его `remove()`
физически вычёркивал запись из файла. Порт `MaintenanceEventRepository`
намеренно не имеет метода удаления, и это записано в самом контракте, — но
адаптер истории обращался к файлу напрямую, минуя порт.

### 3. Групповая проверка писалась по одной записи

Проверка склада — до 260 огнетушителей на три вида работ. Записи сохранялись
циклом с выходом по первой ошибке: сбой на середине оставлял часть проверки
записанной, а убрать её нельзя, потому что записи журнала не удаляются.

## Решение

**Запись атомарна.** `writeJsonAtomically` пишет во временный файл, вызывает
`sync()` и переименовывает поверх. Переименование в пределах тома неделимо: на
диске лежит либо целиком старая версия, либо целиком новая.

**Повреждённый файл — ошибка, а не пустота.** Введён код `FILE_CORRUPTED`.
Отсутствие файла по-прежнему даёт пустой список — это обычное состояние до
первой записи. Ошибка разбора возвращается наверх, и хранилище **не пишет**
поверх такого файла: испорченные данные остаются на диске и подлежат
восстановлению.

**Журнал не откатывается.** `CommandHistory.record` не принимает изменения вида
`maintenance`, поэтому действие, состоящее только из записи проверки, выходит
пустым и на стек отмены не ложится. Дополнительно заведён `appendOnlyAdapter`:
даже если запись туда попадёт, правка и удаление будут отклонены. Ошибка
исправляется новой записью, как зачёркивание в бумажном журнале, а не вырванным
листом.

**Массовая запись неделима.** В портах появился `saveMany`, в ядре —
`recordMaintenanceBatch`. Порядок обязателен: сначала проверяются и собираются
все события до единого, и только потом они ложатся на диск одной операцией.
Отказ означает, что не записано ничего.

## Последствия

- Хранилища больше не решают эти вопросы каждое по-своему: и чтение, и запись
  идут через `json-store.ts`. Переход на SQLite снимет заботу целиком —
  атомарность и целостность станут задачей базы.
- Возврат `Result` из чтения обязал вызывающих обрабатывать ошибку. Молчаливое
  «список пуст» больше невозможно.
- `saveMany` попутно убрал перезапись всего файла на каждый объект: применение
  настроек к 123 огнетушителям занимало 0,9 с, теперь это одна запись.

## Проверка

`json-store.test.ts` и `command-history.test.ts` закрепляют поведение:
повреждённый файл даёт `FILE_CORRUPTED` и остаётся нетронутым; отмена возвращает
правку карточки, но оставляет проведённую проверку в журнале.
